# QMonitoring Rebar Review MVP 0.1.3

Revit 2024 / pyRevit / IronPython 2.7. Это отдельный **review-only** путь для
полной партии прямых `graphic-bar-plan-draft/v1` или
`graphic-bar-plan-pruned/v1` или `graphic-bar-plan-repaired/v1`. Он создаёт настоящие `DB.Structure.Rebar`, но не
является инженерным выпуском. Первый запуск всей партии в настоящем Revit ещё
не выполнен.

## Установка и запуск

1. Распакуй code-only ZIP в `C:\QMonitoring\RebarReview\`: внутри этой папки
   должна находиться `QMonitoringRebarReview.extension`. В pyRevit Settings →
   Custom Extension Directories добавь именно `C:\QMonitoring\RebarReview\`
   (не ZIP, не `script.py`, не саму `.extension`). Reload. Старые инструменты не отключай.
2. Открой локальную либо отсоединённую **КОПИЮ** Revit 2024. Central/cloud
   блокируются. Выдели одну native Floor, **соответствующую выбранному JSON**:
   Пм-1 К09 для JSON К09; С1 — только для отдельного JSON С1. Не произвольную плиту.
   Для С1 наличие matching Floor в переданных RVT не подтверждено: если её нет, подготовь
   соответствующую плоскую native Floor в отдельной копии штатными средствами
   Revit. Плагин Floor не создаёт и геометрию DXF с RVT автоматически не совмещает.
3. Нажми `QMonitoringRebarReview → Review → Rebar Review`, выбери полный JSON,
   новый путь обязательного отчёта и явный XY-перенос.
   Масштаб/поворот не угадываются; глубины не берутся из DXF и не называются cover.
4. Для каждого сочетания steel/D выбери точный загруженный RebarBarType. В проекте
   должна быть совместимая существующая прямая RebarShape: новую форму команда
   не создаёт. Оба
   диаметра типа — nominal/model — должны совпасть с JSON до 0,001 мм.
5. Подтверди автоматически предложенные глубины осей по native-граням и Dmax
   выбранных типов. Профиль MVP: отступ тела от грани40мм и вертикальный зазор4мм,
   не Revit cover и не норматив. Ручной ввод — только «Другие настройки».
   Подтверди копию и создание всей партии. До 5000 отдельных Rebar может занять
   заметное время. Ничего не пропускается ради успеха.
6. После Commit плагин перечитывает каждый созданный ID, host, тип, comment с
   исходным bar ID, единственную конечную прямую ось XYZ, длину, D и количество.
   Масса выводится из считанных осей по `0.000006165·d²·L`; это не измеренная
   плотность материала Revit. Допуск оси/длины — 0,01 мм.
7. Только после успешной полной сверки появится отдельный вопрос: оставить
   диагностические Rebar в копии или откатить всю партию. Keep фиксирует группу,
   но не вызывает Save/Sync. Отказ, отмена, warning/error либо расхождение
   откатывают весь набор. При неподтверждённом откате закрой копию без сохранения.

## Честные границы MVP

Проверяются одна planar top face, одна planar bottom face, совпадающие native
внешние line-loop контуры и толщина выбранной Floor. BBox не используется.
Тело прямого стержня должно лежать внутри внешнего контура/толщины. Внутренние
loops считываются, но **отверстия исключены**; cover только сохраняется как
metadata и не блокирует. Перепады, наклон, несколько граней, кривые и неоднозначный
контур блокируются как unsupported. Это не actual-Solid containment proof.

### К09 Пм-1

Выдели native Floor Пм-1 в КОПИИ К09 (в проверенном snapshot ID11020633),
не плиту С1. Толщина200мм, native bottom Z6910 / top Z7110мм в этом snapshot.
Top57/bottom75 наружных вершин отличаются не только разбиением: наtop есть
дополнительный вырез300×180мм. Профиль
`flat200-top-subset-bottom-dual-exterior-mvp/v1` проверяет flat±Z,200мм,
полное вложение top-контура в bottom и тело КАЖДОГО стержня в ОБОИХ контурах.
ID не является доказательством: та же геометрия в новой копии поддержана и с новымID.
BBox не используется, промежуточный Solid не сертифицируется. При выходе хотя бы
одного тела вся партия блокируется доCommit; клиппинга/пропуска нет.
Computational EPS внешнего контура — 0,000001мм (шум перевода футов), не
инженерный зазор. Выход0,1мм отвергается. Readback XYZ/длины остаётся0,01мм.
Выбери полный JSON именноК09 и явный XY-перенос; глубины предложит команда. Не используй
С1JSON илиDXFZ как глубины. Нужны существующие прямые RebarShape и точные D/steel.
40d/stock/conditional3Dfail остаются видимыми. Живой Revit ещё не проверен.

Для текущей полной К09 dual-exterior партии (918 стержней) автоматическое
диагностическое предложение — **`46;62;48;68`** мм в порядке низX;низY;верхX;верхY.
Это расстояния от native-грани до ОСИ, не cover. Ноль ставит ось на грань,
половина тела окажется снаружи — такой пакет блокируется.
При native Z 6910..7110 получаются оси 6956;6972;7062;7042 мм. В этой партии
максимальные D: низ 12 / верх 16 мм. Нижние и верхние ортогональные тела имеют минимум 4 мм,
верх-низ 56 мм вертикального зазора. Вся партия 918 проходит native
двухконтурный preflight offline с этим профилем. Это не проверка отверстий,
фона, всех коллизий одного направления, cover или engineering approval. Исходные
40d/stock/conditional 3D fail не снимаются; выбранные Z не сертифицированы.

Формула отдельно для каждого слоя: rX=DmaxX/2, rY=DmaxY/2;
depthX=40+rX, depthY=depthX+rX+4+rY. Пустое направление не создаёт стержней;
если X пусто, единственное Y получает40+rY. Native cover не используется.
Перед созданием профиль и глубины точно сверяются с повторным native-readback
граней/типов. Недостаточная толщина или зазор блокируют auto-профиль.
Например Ø36 во всех четырёх направлениях требует минимум236мм толщины.
«Другие настройки» сохраняет ручной review-путь, но не объявляет auto-gap пройденным.
Отчёт содержит axis_depth_policy, вычисленные/подтверждённые глубины и auto/manual provenance.

При раннем отказе до выбора пути отчёта setupJSON сохраняется под уникальным
именем `qmonitoring-rebar-review-setup-*.json` в Windows `%TEMP%`.
Окно показывает причину и точный путь; полный traceback — в выводе pyRevit иJSON.

Исходные `coverage`, `40d`, `stock`, collision и другие `fail/not_checked` не
исправляются и не скрываются. Фон, существующие Rebar, загибы, муфты и формы не
создаются и не меняются. Отсутствие проверки отверстий/cover/фона означает
`not_checked`, а не pass. `placement_eligible=false` и
`engineering_approval=false` сохраняются даже после Keep.

В ZIP нет RVT/DXF/RFA/JSON проекта. Manifest содержит whitelist и SHA256.

Repaired JSON — отдельная полная партия после trim с retained/modified/added,
точными исходными bytes/SHA и известными исходными lane/FE. Команда проверяет
согласованность транспорта, а не повторяет FE-доказательство в Revit.
Свежие coverage/40d/stock и условные collision-статусы записываются в отчёт;
actual RVT collision остаётся not_checked. Новый JSON не даёт engineering approval.
Условные исходные3D-статусы относятся к ResearchLayerProfile с Z, зависящим отD.
Четыре фиксированные глубины осей, введённые вUI, — другой профиль: их readback
строгий, но отдельная collision-проверка для этих выбранныхZ не выполняется.
