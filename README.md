# Rebar Auto-Layout — Qmonitoring × A101

Python-ядро для автоматической раскладки дополнительного армирования железобетонных
плит по цветовым мозаикам (изополям) ЛИРА-САПР.

Вход — четыре направления одной плиты: `{нижнее, верхнее} x {ось X, ось Y}` в DXF
(позже PNG). Выход всего пайплайна — прямоугольные участки стержней с диаметром, шагом,
длиной и количеством, подготовленные для передачи в Revit-плагин.

## Важное понимание задачи

Цвет конечного элемента задаёт локально требуемый уровень армирования, но не является
жёсткой границей выходной детали. Прямоугольник может включать несколько цветов и даже
область без потребности в дополнительной арматуре: это допустимый перерасход, которым
алгоритм балансирует против количества деталей.

Подробная постановка и нерешённые инженерные вопросы находятся в
[`docs/optimization-notes.md`](docs/optimization-notes.md), устройство взаимозаменяемых
алгоритмов — в [`docs/optimization-architecture.md`](docs/optimization-architecture.md).

## Статус

### Готово: стадия A — DXF ingest

- разбор `.shk` и подписей арматуры;
- чтение `3DFACE` слоя `KLEENKA` и удаление служебных копий `PLAST`;
- треугольные и четырёхугольные КЭ;
- извлечение ACI-порядка шкалы и интервалов `As` из блока `KLEENKA`;
- автоматическое определение входных единиц (метры/миллиметры) и нормализация в мм;
- определение направления армирования из имени файла;
- поиск совместимого `.shk`, если он доступен;
- диагностический PNG-рендер и HTML-отчёт;
- 23 теста, включая прогоны на реальных файлах организаторов.

### Готово: каркас локального MVP оптимизации

- единые контракты `LayoutProblem` и `LayoutSolution`, не меняющие `Mosaic`;
- адаптер `Mosaic -> DemandMap -> LayoutProblem`;
- registry для выбора алгоритма по имени;
- алгоритмы `bbox` и `bsp` в отдельных модулях;
- общие детализация, расчёт массы, валидация и метрики;
- автономный HTML/SVG-отчёт сравнения и общий `solutions.json`;
- 11 тестов контракта, алгоритмов и отчёта, включая реальный DXF.

Оба алгоритма пока являются baseline. Это ещё не финальная инженерная раскладка: правила
покрытия, зазоров и геометрии проёмов требуют подтверждения. `LayoutZone` уже соответствует
требуемому ТЗ типу выхода: прямоугольник, длина, ширина, диаметр, шаг и количество.

### Не реализовано

- fallback-парсер PNG (`src/rebar/png_ingest.py`);
- стадия B: точные пороговые области и правило одиночного КЭ;
- стадия C: точная генерация допустимых прямоугольников с кратностью шагу, `40d` и
  зазорами между соседними зонами;
- стадия D: CP-SAT/MILP, Парето-кривая «масса ↔ число деталей» и «Точка 3»;
- экспорт промежуточного результата для Revit.

Следующий этап нельзя сводить к независимому обведению областей одного цвета. Перед
реализацией оптимизатора нужно закрыть вопросы из `docs/optimization-notes.md` о
пересечениях деталей и способе проверки достаточности `As`.

Оптимизируем именно прямоугольные зоны. Ядро обязано вычислить их положение, длину с
`40d`, ширину `k × step`, диаметр, шаг, количество `k + 1`, массу и взаимные зазоры.
Размещение реальных семейств арматуры по этим параметрам относится к Revit-плагину.

## Структура

```text
src/rebar/
  models.py          публичный контракт Mosaic, Cell, Band, Direction, Rebar
  legend.py          .shk + подписи арматуры -> Band
  dxf_ingest.py      DXF -> Mosaic
  render.py          Mosaic -> диагностический PNG
  png_ingest.py      заготовка PNG fallback
  optimization/
    contracts/       единые LayoutProblem и LayoutSolution
    adapters/        Mosaic -> задача оптимизации
    services/        общие геометрия, детализация и проверка
    algorithms/      отдельные bbox.py, bsp.py; здесь появятся greedy.py/cpsat.py
    registry.py      выбор реализации по стабильному имени
  reporting/         автономные SVG/HTML-отчёты, отдельно от ядра оптимизации
scripts/
  verify_stage_a.py  HTML-отчёт по реальному датасету
  compare_optimizers.py  локальное сравнение алгоритмов
tests/
  test_stage_a.py    модульные и интеграционные тесты стадии A
  optimization/      тесты по тем же архитектурным слоям
docs/
  context.md                 общий контекст и проверенные факты
  stage-a-parser-spec.md     спецификация завершённой стадии A
  optimization-notes.md     постановка стадий B-D и открытые вопросы
  optimization-architecture.md  контракт и порядок добавления алгоритмов
```

## Требования и установка

- Python 3.10 или новее;
- зависимости перечислены в `requirements.txt`.

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
```

## Данные организаторов

Каталог `Дополнительные материалы/` не публикуется в GitHub: он содержит тяжёлые и
потенциально непубличные DXF/DWG/PDF/PNG/PCP/LIR-файлы.

Для полного локального прогона получите набор отдельно и положите его в корень проекта:

```text
qmonitoring-a101-project/
  Дополнительные материалы/
    Изополя(мозаики) армирования/
    Для верификации изополей/
    Для верификации изополей 2/
    ...
```

Пути содержат кириллицу, пробелы и иногда разные Unicode-нормализации. Не переименовывайте
исходники без необходимости. Интеграционные тесты без локальных файлов пропускаются.

## Запуск парсера

```python
from rebar.dxf_ingest import read_mosaic

mosaic = read_mosaic(
    "Дополнительные материалы/Нижнее армирование вдоль ОСИ Х.dxf",
    # shk_path можно не передавать: парсер попробует найти совместимый файл рядом.
)

print(mosaic.direction)
print(len(mosaic.cells))
print(mosaic.bbox)  # всегда миллиметры
print(mosaic.meta["unit_detection"])
```

При запуске файла напрямую из корня добавьте `src` в `PYTHONPATH` либо установите проект
в editable-режиме:

```bash
python3 -m pip install -e .
```

## Автоматическая проверка

```bash
python3 -m pytest -q
python3 -m ruff check src tests scripts
python3 -m compileall -q src tests scripts
```

На полном локальном датасете ожидается `34 passed`. Без датасета тесты, зависящие от
реальных файлов, будут отмечены как `skipped`.

GitHub Actions запускает те же проверки на каждый push и pull request:

- установка пакета на минимально поддерживаемом Python 3.10;
- Ruff;
- pytest с явным отчётом о пропущенных интеграционных тестах;
- `compileall`;
- сборка wheel.

Реальные материалы организаторов в CI не загружаются. Полный интеграционный прогон и
визуальный отчёт выполняются локально перед merge.

## Визуальная проверка стадии A

```bash
python3 scripts/verify_stage_a.py
```

Отчёт создаётся в `artifacts/stage_a_verification/index.html`. В нём исходный PNG
сравнивается с нашим рендером из DXF; дополнительно показываются число КЭ, bbox, единицы,
цвета и структурные проверки.

Можно передать свои пути:

```bash
python3 scripts/verify_stage_a.py \
  --data-dir "/path/to/Дополнительные материалы" \
  --out-dir "/path/to/report"
```

## Локальное сравнение алгоритмов

Для DXF, рядом с которым парсер может найти совместимый `.shk`:

```bash
python3 scripts/compare_optimizers.py \
  "Дополнительные материалы/Нижнее армирование вдоль ОСИ Х.dxf" \
  --algorithms bbox bsp \
  --max-details 4
```

Откройте `artifacts/comparison/index.html`. Внешних картинок и абсолютных путей в нём
нет: мозаика и детали встроены как inline SVG. Рядом находится `solutions.json` с
одинаковой схемой результатов всех алгоритмов.

Переключение из Python:

```python
from rebar.optimization import AlgorithmRequest, built_in_optimizer_registry

registry = built_in_optimizer_registry()
optimizer = registry.create("bsp")  # либо "bbox", позже "greedy" / "cpsat"
solution = optimizer.solve(problem, AlgorithmRequest(max_details=4))
```

Текущие аппроксимации и инструкция по добавлению нового метода описаны в
[`docs/optimization-architecture.md`](docs/optimization-architecture.md).

## Пайплайн

```text
DXF/PNG
  -> A. Ingest: Mosaic
  -> B. Demand map: уровни требований и пороговые области
  -> C. Rectangularization: допустимые прямоугольные детали
  -> D. Detailing + optimization: масса, анкеровка, коллизии, «Точка 3»
  -> E. Промежуточный JSON для Revit
```

Полный контекст проекта: [`docs/context.md`](docs/context.md).
