# Rebar Auto-Layout — Qmonitoring × A101

Python-ядро для автоматической раскладки дополнительного армирования железобетонных
плит по цветовым мозаикам (изополям) ЛИРА-САПР.

Вход — четыре направления одной плиты: `{нижнее, верхнее} x {ось X, ось Y}` в DXF
(позже PNG). Выход всего пайплайна — прямоугольные участки стержней с диаметром, шагом,
длиной и количеством, подготовленные для передачи в Revit-плагин.

## Важное понимание задачи

Цвет конечного элемента задаёт локально требуемый уровень армирования, но не является
жёсткой границей выходной зоны. Прямоугольник может включать несколько цветов и даже
область без потребности в дополнительной арматуре: это допустимый перерасход, которым
текущий алгоритм балансирует против числа зон.

После сверки с готовым проектом различаем три счётчика: `len(zones)` — параметрические
прямоугольные зоны, `sum(zone.bar_count)` — физические стержни, число строк/марок
спецификации — номенклатура после группировки. Поле `detail_count` пока хранит число зон,
но его нельзя без подтверждения приравнивать к «деталям» на графике ТЗ. Текущий отчёт
оптимизаторов работает с одним направлением; итоговые метрики плиты должны суммировать
четыре направления.

Подробная постановка и нерешённые инженерные вопросы находятся в
[`docs/optimization-notes.md`](docs/optimization-notes.md), устройство взаимозаменяемых
алгоритмов — в [`docs/optimization-architecture.md`](docs/optimization-architecture.md),
их пошаговая работа и Mermaid-схемы — в [`docs/algorithms.md`](docs/algorithms.md),
первый эталон инженера — в [`docs/golden-case.md`](docs/golden-case.md),
ближайший план — в [`docs/mvp-roadmap.md`](docs/mvp-roadmap.md).

## Статус

### Готово: стадия A — DXF ingest

- разбор `.shk` и подписей арматуры;
- чтение `3DFACE` слоя `KLEENKA` и удаление служебных копий `PLAST`;
- треугольные и четырёхугольные КЭ;
- извлечение ACI-порядка шкалы и интервалов `As` из блока `KLEENKA`;
- автоматическое определение входных единиц (метры/миллиметры) и нормализация в мм;
- определение направления армирования из имени файла;
- поиск совместимого `.shk`, если он доступен;
- диагностический PNG-рендер и HTML-отчёт;
- 23 теста, включая прогоны на реальных файлах организаторов.

### Готово: каркас локального MVP оптимизации

- единые контракты `LayoutProblem` и `LayoutSolution`, не меняющие `Mosaic`;
- адаптер `Mosaic -> DemandMap -> LayoutProblem`;
- отдельный mapping-слой для DXF без `.shk`: таблица `plate-zero-d12-v1` связывает
  шесть уровней плиты нуля с фоном `⌀12/300` и дополнительной арматурой;
- registry для выбора алгоритма по имени;
- алгоритмы `bbox`, `bsp`, быстрый полосовой `greedy`, цвето-приоритетный
  `greedy-priority` и bottom-up `agglomerative` в отдельных модулях;
- общие детализация, расчёт массы, валидация и метрики;
- автономный HTML/SVG-отчёт сравнения и общий `solutions.json`;
- строгий общий конструктор и независимый валидатор: полная геометрия КЭ, ширина
  `k × step`, `bar_count = k + 1`, выпуски `40d`, масса, пересечения и зазоры;
- golden-case плиты нуля: 4 листа, 79 позиций, 1019 стержней, 3177,64 кг;
- проверка таблиц исходного PDF и автономный HTML с входными изополями и ручным
  решением инженера;
- 23 теста контракта, алгоритмов и инженерных правил плюс 6 golden-тестов, включая
  реальные DXF и PDF.

Все алгоритмы пока являются baseline. Это ещё не финальная инженерная раскладка: правило
зазора для зон с разным шагом и геометрия проёмов требуют подтверждения. `LayoutZone` уже
соответствует требуемому ТЗ типу выхода: прямоугольник, длина, ширина, диаметр, шаг и
количество.

### Не реализовано

- fallback-парсер PNG (`src/rebar/png_ingest.py`);
- стадия B: точные пороговые области и правило одиночного КЭ;
- стадия C: исчерпывающая генерация допустимых прямоугольников (`CandidateSet`);
- стадия D: CP-SAT/MILP, Парето-кривая «масса ↔ число зон» и сопоставление с «Точкой 3»;
- агрегация четырёх направлений в `PlateSolution` и общеплитный Парето-фронт;
- экспорт промежуточного результата для Revit.

Следующий этап нельзя сводить к независимому обведению областей одного цвета. Перед
реализацией оптимизатора нужно закрыть вопросы из `docs/optimization-notes.md` о
пересечениях деталей и способе проверки достаточности `As`.

Оптимизируем именно прямоугольные зоны. Ядро обязано вычислить их положение, длину с
`40d`, ширину `k × step`, диаметр, шаг, количество `k + 1`, массу и взаимные зазоры.
Размещение реальных семейств арматуры по этим параметрам относится к Revit-плагину.

## Требования и установка

- Python 3.10 или новее;
- зависимости перечислены в `requirements.txt`.

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
```

## Данные организаторов

Каталог `Дополнительные материалы/` не публикуется в GitHub: он содержит тяжёлые и
потенциально непубличные DXF/DWG/PDF/PNG/PCP/LIR-файлы.

`.shk` — шкала конкретной расчётной выдачи, а не глобальная настройка проекта. Для
автовыбора должны совпасть число цветовых полос и, при необходимости, ось X/Y; при
неоднозначности передавайте совместимый `shk_path` явно.

Для golden-case плиты нуля `.shk` отсутствует. Его шесть назначений вручную перенесены
из легенд PNG в таблицу `plate-zero-d12-v1`. Это явно помеченное MVP-допущение только
для этого комплекта, а не fallback для произвольной плиты.

Для полного локального прогона получите набор отдельно и положите его в корень проекта:

```text
qmonitoring-a101-project/
  Дополнительные материалы/
    Изополя(мозаики) армирования/
    Для верификации изополей/
    Для верификации изополей 2/
    ...
```

Пути содержат кириллицу, пробелы и иногда разные Unicode-нормализации. Не переименовывайте
исходники без необходимости. Интеграционные тесты без локальных файлов пропускаются.

## Запуск парсера

```python
from rebar.dxf_ingest import read_mosaic

mosaic = read_mosaic(
    "Дополнительные материалы/Нижнее армирование вдоль ОСИ Х.dxf",
    # shk_path можно не передавать: парсер попробует найти совместимый файл рядом.
)

print(mosaic.direction)
print(len(mosaic.cells))
print(mosaic.bbox)  # всегда миллиметры
print(mosaic.meta["unit_detection"])
```

Для одного из четырёх DXF плиты нуля после ingest применяется явная таблица:

```python
from rebar.optimization import PLATE_ZERO_D12, apply_rebar_mapping, build_layout_problem

mapped_mosaic = apply_rebar_mapping(mosaic, PLATE_ZERO_D12)
problem = build_layout_problem(mapped_mosaic)

print(mapped_mosaic.meta["rebar_mapping"])
```

`apply_rebar_mapping` возвращает копию и откажется работать, если шкала отличается,
содержит неизвестный ACI или в `Mosaic` уже есть легенда из `.shk`.

При запуске файла напрямую из корня добавьте `src` в `PYTHONPATH` либо установите проект
в editable-режиме:

```bash
python3 -m pip install -e .
```

## Автоматическая проверка

```bash
python3 -m pytest -q
python3 -m ruff check src tests scripts
python3 -m compileall -q src tests scripts
```

На полном локальном датасете ожидается `61 passed`. Без датасета тесты, зависящие от
реальных файлов, будут отмечены как `skipped`.

GitHub Actions запускает те же проверки на каждый push и pull request:

- установка пакета на минимально поддерживаемом Python 3.10;
- Ruff;
- pytest с явным отчётом о пропущенных интеграционных тестах;
- `compileall`;
- сборка wheel.

Реальные материалы организаторов в CI не загружаются. Полный интеграционный прогон и
визуальный отчёт выполняются локально перед merge.

## Визуальная проверка стадии A

```bash
python3 scripts/verify_stage_a.py
```

Отчёт создаётся в `artifacts/stage_a_verification/index.html`. В нём исходный PNG

```bash
  --out-dir "/path/to/report"
```

## Локальное сравнение алгоритмов

Текущая команда сравнивает алгоритмы **на одном направлении**. Для DXF, рядом с которым
парсер может найти совместимый `.shk`:

```bash
python3 scripts/compare_optimizers.py \
  "Дополнительные материалы/Нижнее армирование вдоль ОСИ Х.dxf" \
  --algorithms bbox bsp greedy greedy-priority agglomerative \
  --max-details 4
```

Откройте `artifacts/comparison/index.html`. Внешних картинок и абсолютных путей в нём
нет: мозаика и зоны встроены как inline SVG. Рядом находится `solutions.json` с
одинаковой схемой результатов всех алгоритмов.

`--max-details 4` — намеренно маленькое ограничение для smoke-теста. Полученные `1/4`
зоны нельзя сравнивать с графиком всей плиты из ТЗ и нельзя считать выбранной
«Точкой 3».

Переключение из Python:

```python
from rebar.optimization import AlgorithmRequest, built_in_optimizer_registry

registry = built_in_optimizer_registry()
optimizer = registry.create("agglomerative")  # также bbox / bsp / greedy / greedy-priority
solution = optimizer.solve(problem, AlgorithmRequest(max_details=4))
```

Текущие аппроксимации и инструкция по добавлению нового метода описаны в
[`docs/optimization-architecture.md`](docs/optimization-architecture.md).

## Golden-case: сравнение с инженером

Первый эталон — плита нуля корпуса 2.9. Команда заново читает спецификации страниц 8-11
готового PDF, проверяет `79` позиций, `1019` физических стержней и `3177,64` кг, затем
встраивает четыре исходных изополя и четыре листа инженера в один HTML:

```bash
python3 scripts/verify_golden_case.py
```

Откройте `artifacts/golden_plate_zero/index.html`. Картинки хранятся внутри HTML как
`data:`-URI, поэтому отчёт работает после переноса без каталога `artifacts` и без
интернета. Рядом создаётся `golden.json` со строками спецификаций.

Для чтения и рендера PDF нужен Poppler (`pdftotext`, `pdftoppm`; на macOS —
`brew install poppler`). Числовую часть можно проверить отдельно:

```bash
python3 -m pytest -q tests/golden
```

Сейчас это эталон массы, количества стержней и номенклатуры. Автоматическое сравнение
геометрии зон потребует конвертации готовых DWG в DXF. Детали и ограничения описаны в
[`docs/golden-case.md`](docs/golden-case.md).

## Пайплайн

```text

  -> A. Ingest: Mosaic
  -> B. Demand map: уровни требований и пороговые области
  -> C. Rectangularization: допустимые прямоугольные зоны
  -> D. Detailing + optimization: масса, анкеровка, коллизии, «Точка 3»
  -> E. Промежуточный JSON для Revit
```

Полный контекст проекта: [`docs/context.md`](docs/context.md).
