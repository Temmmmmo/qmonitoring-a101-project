# AGENTS.md — инструкция для кодовых агентов

Проект автоматизирует раскладку дополнительной арматуры плит (Qmonitoring × A101).
Алгоритмическое ядро написано на Python; ЛИРА-САПР, AutoCAD и Revit находятся вне
этого репозитория.

## Текущее состояние

Стадия A для DXF реализована и проверена:

- `src/rebar/legend.py` — `.shk` и подписи арматуры -> `list[Band]`;
- `src/rebar/dxf_ingest.py` — `3DFACE`/`KLEENKA` -> `Mosaic`;
- `src/rebar/render.py` — диагностический PNG;
- `scripts/verify_stage_a.py` — переносимый HTML-отчёт;
- `tests/test_stage_a.py` — 23 теста на полном локальном датасете;
- входные метры и миллиметры автоматически нормализуются в мм.

Добавлен каркас поздних стадий:

- `optimization/contracts/` — единые вход и выход всех методов;
- `optimization/adapters/` — граница с `Mosaic`;
- `optimization/mappings/` — явные проверяемые таблицы для DXF без `.shk`; для плиты
  нуля реализована `plate-zero-d12-v1` со статусом MVP-допущения;
- `optimization/services/` — общие формулы и независимая проверка;
- `optimization/algorithms/` — отдельный модуль на каждый алгоритм (`bbox`, `bsp`,
  `greedy`, `greedy-priority`, `agglomerative`, `row-run-greedy`,
  `strip-profile-dp`, `spatial-partition-greedy`);
- `reporting/` и `scripts/compare_optimizers.py` — локальное сравнение через SVG/HTML.
- `golden/` и `scripts/verify_golden_case.py` — проверка PDF-спецификаций плиты нуля и
  автономный HTML «изополе ↔ решение инженера»; на полном датасете golden-тест фиксирует
  79 позиций, 1019 физических стержней и 3177,64 кг.
- `application/analyze_direction.py` — единый сценарий анализа одного DXF без
  дублирования parser/mapping/optimizer-логики;
- `web/app.py` и `web/static/` — локальный FastAPI + статический интерфейс одного
  направления; upload живёт только во временном каталоге, БД и очередей нет.

Это baseline с явно указанными аппроксимациями, не готовая инженерная выдача.
`src/rebar/png_ingest.py` пока является заготовкой.

Важно: `LayoutZone` — целевой параметрический результат ядра, а не временная оболочка для
будущего `PlacedBar`. ТЗ требует прямоугольник, длину, ширину, диаметр, шаг и количество;
реальные семейства стержней размещает Revit-плагин.

## Текущий приоритет

Следующий этап — не «выделить независимые компоненты каждого цвета», а построить карту
локальных требований к армированию и подготовить корректную постановку прямоугольного
покрытия.

Критически важное понимание:

- цвет КЭ задаёт требуемый уровень, но не жёсткую границу детали;
- выходной прямоугольник может включать несколько цветов и область без потребности;
- лишнее покрытие допустимо и учитывается как перерасход массы;
- недоармирование недопустимо;
- пересечения зон разрешены; пока одна достаточная зона должна сама обеспечить уровень
  КЭ, а `As` нескольких слабых зон не суммируется;
- `40d` и раздвижка крайних стержней выполняются общей постобработкой и не заставляют
  алгоритм сливать прямоугольники;
- итоговую массу и Парето-метрики считать после этой постобработки.

Общий конструктор считает ширину `k × step`, `bar_count = k + 1`, фазу/оси стержней,
длину с заменяемой политикой `40d`, раскрой, покрытие и массу. Алгоритмы и hard-валидатор
разрешают пересекающиеся `demand_bbox`; площадь покрытия считается по геометрическому
объединению, чтобы overlap не засчитывался дважды. Один КЭ может быть покрыт одной зоной
или объединением частей зон, каждая из которых самостоятельно имеет достаточный уровень.
Установленный envelope после `40d`, реальные линии и зазор крайних осей проверяются
отдельной постобработкой и не вызывают forced merge. `allow_overlaps=False` оставлен
только как прежний строгий исследовательский профиль.

Для демонстрации к 20 августа текущий пользовательский скоуп сокращён до одного DXF.
`spatial-partition-greedy` строит регулярную маску из геометрии КЭ, сам начинает с
непересекающихся прямоугольников и укрупняет их только через плитки, где существует
геометрия `KLEENKA`. На C1 при лимите 32 он сохраняет 32 зоны и 12 недоминируемых точек
своей жадной траектории; непересечение здесь свойство алгоритма, а не инженерный запрет.
Это контрольный baseline, а не доказанный глобальный Парето-фронт. Следующий приоритет —
визуальная сверка C1, оценка чувствительности, эвристический поиск (в том числе
генетический алгоритм) и сравнение с геометрией инженера. `PlateProblem`/`PlateSolution`,
полный `CandidateSet`, CP-SAT/MILP и общий Парето-фронт остаются следующими этапами.

Golden-case плиты нуля можно превратить в четыре `LayoutProblem` без `.shk` через
`apply_rebar_mapping(mosaic, PLATE_ZERO_D12)`. Таблица применяется только после ingest,
проверяет всю шкалу, не перезаписывает существующую легенду и не считается подходящей
для других плит без отдельного подтверждения.

Не смешивать уровни метрик: `len(zones)` — число параметрических зон, сумма `bar_count`
— число физических стержней, а число позиций спецификации получается только после
группировки одинаковых стержней. Поле `LayoutMetrics.detail_count` пока исторически
означает число зон; не объявлять его эквивалентом колонки `Кол-во, шт.` или оси графика
ТЗ. `LayoutSolution` относится к одному направлению. Для итогового графика плиты нужен
планируемый агрегат четырёх направлений `PlateSolution`; результаты однонаправленного
smoke-теста baseline с маленьким лимитом не являются «Точкой 3».

В локальных материалах найдено 15 четырёхнаправленных входных наборов, но только 11
независимых объединённых инженерских выдач и ни одной явно размеченной «Точки 3».
Поэтому не обучать ML, который напрямую выдаёт арматуру. Допустимый первый эксперимент —
калибровка одного веса или положения на Парето-кривой по финальным решениям инженеров с
leave-one-project-out проверкой. Новые оптимизаторы добавлять отдельными файлами в
`optimization/algorithms/`; не помещать в них сериализацию, HTML или собственную версию
расчёта общих метрик.

## Как установить и проверить

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
python3 -m pip install -e .
```

```bash
python3 -m pytest -q
python3 -m ruff check src tests scripts
python3 -m compileall -q src tests scripts
```

Визуальная проверка:

```bash
python3 scripts/verify_stage_a.py
python3 scripts/verify_golden_case.py
python3 -m uvicorn rebar.web.app:app --app-dir src --reload
```

Результаты: `artifacts/stage_a_verification/index.html` и
`artifacts/golden_plate_zero/index.html`. Web-интерфейс открывается по
`http://127.0.0.1:8000`.

Production-схема описана в [`docs/deployment.md`](docs/deployment.md): контейнер не
публикует порт на хосте, подключается к внешней `caddy_net`, а deploy запускается на
self-hosted runner только после успешного CI для `main`.

## Локальные данные

Реальные файлы находятся в `Дополнительные материалы/`. Каталог целиком исключён из Git:

- он содержит тяжёлые и потенциально непубличные материалы организаторов;
- тестовые фикстуры ищут данные по относительной структуре и корректно пропускают тест,
  если нужного файла нет;
- пути содержат кириллицу, пробелы и разные Unicode-нормализации;
- пути принимать как аргументы или задавать в `tests/conftest.py`, не размазывать
  хардкод по коду.

## Неизменяемые соглашения

- Все координаты и длины внутри ядра — в миллиметрах.
- Единицы нормализуются только на границе ingest; решение сохраняется в `Mosaic.meta`.
- Направление — `Direction`, `Layer`, `Axis`, а не строки.
- Для DXF читать результат `3DFACE` только слоя `KLEENKA`; парные копии `PLAST`
  отбрасывать.
- У треугольных КЭ удалять повторную четвёртую вершину.
- Сопоставлять уровни по порядку шкалы, не хардкодить глобальное соответствие ACI -> As.
- Не считать `.shk` глобальным для всех DXF: проверять число полос, ось и контекст
  комплекта; при неоднозначности требовать явный путь.
- Явную таблицу без `.shk` выбирать по идентификатору комплекта, проверять все границы
  шкалы и сохранять её `id/source/status` в `Mosaic.meta`; не применять fallback молча.
- Не менять публичные сигнатуры `models.py` без согласования.
- Новую функцию покрывать тестом; форматные открытия фиксировать в `docs/context.md`.
- Числа golden-case менять только после повторного извлечения из исходного PDF и
  документированного объяснения; картинки и сам PDF в Git не добавлять.
- В пользовательском интерфейсе подписывать отдельно зоны, физические стержни и позиции
  спецификации; неоднозначное слово «детали» без единицы счёта не использовать.
- Не коммитить исходные материалы, `artifacts/`, IDE-файлы и другие тяжёлые бинарники.

## Границы проекта

Не нужно:

- автоматизировать или запускать ЛИРА-САПР;
- строить геометрию непосредственно в Revit/AutoCAD;
- читать DWG без отдельного согласованного конвертера;
- позволять ML обходить анкеровку, минимальную ширину, шаги, коллизии и другие жёсткие
  инженерные правила;
- считать точное совпадение выходных прямоугольников с одноцветными областями требованием.

Нормальная архитектура поздних стадий: ML/калибровка может выбирать предпочтение на
Парето-кривой, а детерминированный оптимизатор обязан гарантировать допустимость деталей.
