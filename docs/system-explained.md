# QMonitoring — как это работает: детальный разбор

Документ для тех, кто хочет понять, что именно делает система, как устроен
генетический алгоритм и как из четырёх DXF-файлов получается набор прямоугольных
зон с параметрами армирования.

Не является инженерным заключением или актом приёмки. Все числа относятся к
конкретным контрольным прогонам К09.

---

## 1. Что делает система в целом

**Задача:** автоматизировать раскладку дополнительного армирования железобетонных плит.

**Вход:** 4 DXF-файла на одну плиту — одно направление армирования каждый:
- Нижнее армирование вдоль X
- Нижнее армирование вдоль Y
- Верхнее армирование вдоль X
- Верхнее армирование вдоль Y

Каждый DXF содержит цветную мозаику (изополя) — карту расчётных ячеек (КЭ),
где цвет показывает требуемую интенсивность армирования в этом месте.

**Выход:** набор прямоугольных зон (`LayoutZone`) дополнительного армирования.
У каждой зоны: положение, ширина, длина, диаметр стержня, шаг, число стержней, масса.
Результат передаётся в Revit через JSON для оформления.

## 2. Пайплайн: от DXF до зон

```
DXF (4 файла)
    │
    ▼
[A] Ingest — чтение геометрии
    │   Каждые 2 3DFACE на слое KLEENKA = 1 КЭ
    │   ACI-цвет → индекс уровня
    │   Автоопределение единиц (метры/мм) → нормализация в мм
    ▼
Mosaic{cells[], legend[], direction, bbox}
    │
    ▼
[A.5] Mapping — назначение арматуры
    │   .shk (шкала ЛИРА) или явная таблица
    │   Уровень → {диаметр, шаг, состав добавок}
    ▼
Band[] + Rebar
    │
    ▼
[B] Demand Map — карта локальных требований
    │   Каждый КЭ: геометрия + требуемый уровень
    │   Правило одиночного КЭ: связный компонент из 1 КЭ
    │       понижается на одну полосу шкалы
    ▼
DemandMap
    │
    ▼
[C] Optimization — выбор прямоугольников
    │   Алгоритм (GA / greedy / bsp / ...)
    │   Выбрывает множество прямоугольных зон
    │   Каждая зона: bbox + уровень арматуры
    ▼
LayoutZone[] (сырые прямоугольники)
    │
    ▼
[D] Postprocessing — физическая детализация
    │   Ширина → k × step, bar_count = k + 1
    │   Длина + 40d анкеровки с двух сторон
    │   Фаза (координата первого стержня)
    │   Раздвижка крайних осей
    │   Масса = 0.006165 × d² × L
    ▼
LayoutZone[] (детализированные)
    │
    ▼
[E] Validation — независимая проверка
    │   Покрытие всех исходных КЭ (геометрическое объединение)
    │   Минимальная ширина
    │   Кратность шагу
    │   Запрещённые позиции А101
    │   Масса пересчитана независимо
    ▼
LayoutSolution (проверенное решение одного направления)
    │
    ▼
[F] Plate Aggregation — сборка всей плиты
    │   4 направления × N вариантов
    │   Комбинирование разных алгоритмов по направлениям
    │   Pareto-отсечение: масса vs сложность
    ▼
PlateParetoFront (множество вариантов всей плиты)
    │
    ▼
[G] Export — JSON для Revit
        Исходные изополя + зоны + параметры
        Физическая партия (отдельно)
        Полный отчёт
```

## 3. Генетический алгоритм: как он работает

`genetic-pareto` — основной оптимизатор. Он возвращает не одну раскладку,
а серию вариантов (`solve_many()`), из которых строится Парето-фронт.

### 3.1. Хромосома

Хромосома — **множество индексов прямоугольников** из предсозданного
`CandidateSet`. Каждый индекс указывает на конкретный допустимый прямоугольник
(позиция + уровень арматуры), который уже проверен на корректность.

Это не координаты, не размеры, не произвольные числа. Алгоритм не «придумывает»
геометрию с нуля — он **выбирает комбинацию** из готового набора вариантов.

### 3.2. Как строится CandidateSet

1. **Пространственная маска.** Область плиты дискретизируется в регулярную сетку
   с шагом ~медианный размер КЭ. Каждая плитка помечается:
   - разрешена, если пересекает хотя бы один КЭ слоя `KLEENKA`;
   - запрещена, если это фон или внешнее пространство.

2. **Начальные атомы.** Одинаковые соседние плитки объединяются в непересекающиеся
   начальные прямоугольники. У каждого — максимальный требуемый уровень.

3. **Merge-траектории.** Несколько воспроизводимых последовательностей слияний
   ортогональных соседей. Слияние разрешено, только если весь новый bbox состоит
   из разрешённых плиток. Каждая траектория сохраняет все промежуточные состояния
   (выбранные и альтернативные bbox).

4. **Послойные мосты.** Дополнительные варианты, позволяющие слабой длинной зоне
   проходить под локальной сильной накладкой без повышения всего bbox.

5. **Frozen baseline.** Допустимые решения `bsp`, `greedy-priority` и `agglomerative`
   добавляются в CandidateSet и начальную популяцию без изменения геометрии.
   Их сеточные индексы нужны только для определения соседства.

### 3.3. Операторы

| Оператор | Что делает |
|----------|-----------|
| `crossover` | Смешивает множества двух родителей: часть индексов от первого, часть от второго |
| `split` | Разбивает один прямоугольник на два ортогональных дочерних |
| `merge` | Сливает два соседних прямоугольника в один общий bbox |
| `shift` | Сдвигает прямоугольник вдоль одной оси на один шаг сетки |
| `change-level` | Меняет уровень арматуры прямоугольника на соседний допустимый |
| `baseline-patch` | Заменяет часть хромосомы на подмножество из baseline-решения |

### 3.4. Политика выбора мутаций: UCB1

По умолчанию используется online UCB1 (Upper Confidence Bound):
- каждый оператор имеет счётчик попыток и накопленный reward;
- reward = улучшение двух Парето-целей (масса + сложность) после применения;
- оператор выбирается по формуле `exploitation + exploration × √(ln(N)/n_i)`;
- `uniform` (равновероятностный выбор) остаётся контрольной политикой.

UCB1 **не обучен на данных инженеров**. Он учится только внутри одного запуска
выбирать полезную следующую мутацию. Для каждого нового запуска счётчики сбрасываются.

### 3.5. Repair

После crossover/mutation хромосома может стать недопустимой:
- не все исходные КЭ покрыты;
- превышен лимит числа зон;
- есть избыточные гены.

**Детерминированный repair:**
1. Находит все непокрытые атомы (плитки сетки, которые должен покрывать хотя бы
   один прямоугольник достаточного уровня).
2. Для каждого непокрытого атома подбирает минимальный прямоугольник из CandidateSet,
   который его закрывает.
3. Удаляет избыточные гены (прямоугольники, покрытие которых полностью дублируется).
4. Пытается уложиться в `max_details`, отбрасывая наименее полезные прямоугольники.

### 3.6. Отбор: NSGA-II-подобный ranking + crowding

Каждая особь имеет два вектора:
- **масса** (минимизация)
- **осложнение** (минимизация): либо число зон, либо число физических стержней

Отбор:
1. **Ranking:** все допустимые особи сортируются по Парето-рангу (ранг 0 = недоминируемые).
2. **Crowding:** внутри одного ранга сохраняется разнообразие по двум осям.
3. **Архив:** внешнее множество недоминируемых точек обновляется после каждого поколения.

### 3.7. Материализация и финальная проверка

После завершения эволюции:
1. Каждая особь архива **материализуется** через общий `build_zone` / `build_zone_from_bbox`.
2. Применяется фазирование (подбор первой оси стержня).
3. Каждый результат **полностью перепроверяется** `evaluate_layout` — независимым
   валидатором, который не доверяет внутренним метрикам GA.
4. Внешний `build_direction_pareto_front` повторно удаляет невалидные, доминируемые
   и эквивалентные результаты.

### 3.8. Параметры по умолчанию

| Параметр | Значение | Описание |
|----------|----------|----------|
| `population_size` | 16 | Размер популяции |
| `generations` | 30 | Число поколений |
| `random_seed` | 42 | Сид для воспроизводимости |
| `crossover_rate` | 0.85 | Вероятность скрещивания |
| `mutation_rate` | 0.35 | Вероятность мутации на хромосому |
| `candidate_window` | 6 | Ширина окна альтернатив CandidateSet |
| `candidate_trajectories` | 3 | Число независимых merge-траекторий |
| `layer_bridge_span` | 6 | Протяжённость послойных мостов |
| `maximum_detail_reduction_per_merge` | 12 | Макс. уменьшение зон одним слиянием |
| `maximum_pool_merges` | 5000 | Лимит слияний в пуле |
| `complexity_axis` | `physical_bar_count` | Ось сложности |
| `operator_policy` | `ucb1` | Политика мутаций |
| `ucb_exploration` | √2 | Коэффициент исследования UCB |
| `local_search_passes` | 4 | Проходы локального поиска (0 — выключено) |
| `coverage_atoms` | `demand_fragments` | Дискретизация покрытия |

### 3.9. Что GA НЕ делает

- Не придумывает геометрию с нуля — выбирает из CandidateSet.
- Не изменяет инженерные правила — все ограничения проверяет общий валидатор.
- Не суммирует слабые зоны — одна зона должна самостоятельно иметь достаточный уровень.
- Не получает доступ к «Точке 3» или данным инженеров.
- Не гарантирует глобальный оптимум — работает в пределах конечного CandidateSet.

## 4. Общие сервисы (общие для всех алгоритмов)

### 4.1. `build_zone` / `build_zone_from_bbox`

Принимает набор КЭ или прямоугольник и выполняет детерминированную детализацию:

1. Берёт bbox выбранных КЭ.
2. Назначает уровень арматуры.
3. Отдельно сохраняет область спроса и требуемую рабочую длину.
4. Применяет политику анкеровки (по умолчанию 40d с двух сторон).
5. Округляет длину вверх по каталогу отрезков.
6. Обеспечивает минимальную поперечную ширину, округляет до `k × step`.
7. Задаёт `bar_count = k + 1`.
8. Считает массу: `0.006165 × d² × L_м`.
9. Подбирает фазу и по возможности раздвигает крайние оси.
10. Фиксирует вклад зоны в покрытие КЭ.

### 4.2. `evaluate_layout`

Независимый валидатор. Не доверяет метрикам алгоритма, пересчитывает всё заново:

- известен ли уровень и соответствует ли ему арматура;
- согласованы ли demand bbox, первая/последняя ось, ширина, анкеровка, длина;
- кратна ли ширина шагу; выполняется ли `bar_count = width / step + 1`;
- покрыта ли полная геометрия каждого КЭ **геометрическим объединением** зон
  достаточного уровня (overlap не засчитывается дважды);
- соблюдён ли лимит зон;
- разрешён ли перерасход;
- не используется ли запрещённая позиция А101;
- совпадает ли масса с независимым расчётом.

### 4.3. Покрытие: ключевое правило

> Один КЭ считается покрытым, когда **площадь геометрического объединения**
> его пересечений с зонами достаточного уровня покрывает полную площадь полигона КЭ.

- Overlap не засчитывается дважды.
- `As` слабых зон не суммируется.
- Один КЭ может быть покрыт одной зоной или объединением частей нескольких зон,
  каждая из которых самостоятельно имеет достаточный уровень.
- Пересечения `demand_bbox` зон разрешены (research-профиль).

## 5. Парето-фронт всей плиты

```
LayoutSolution[] × 4 направления
    │
    ▼
evaluate_layout() повторно для каждого кандидата
    │
    ▼
DirectionParetoFront × 4
    │
    ▼
Комбинации разных алгоритмов по направлениям
(неполное декартово произведение: доминируемые частичные суммы удаляются сразу)
    │
    ▼
PlateSolution[]
    │
    ▼
PlateParetoFront(mass, complexity_axis)
```

Оси фронта:
- **Масса** (кг) — суммарная масса добавок по четырём направлениям.
- **Сложность** — либо число зон, либо число физических стержней (выбирается явно).

Дополнительно для каждой точки сохраняются:
- число позиций спецификации (после группировки одинаковых стержней);
- уникальные диаметры, шаги, установленные длины;
- число предупреждений.

**Важно:** текущий фронт ограничен финальными решениями выбранных алгоритмов.
Это честный конечный фронт, но не доказанный глобальный оптимум.

## 6. Физическая постобработка (отдельно от GA)

После выбора параметрических зон выполняется дополнительная обработка:

1. **Схемы СТО** — точные периодические оси (например, @150 = чередование 100/200).
2. **Нормализация** — объединение совпадающих осей, перебалансировка длин.
3. **Раскрой 11 700 мм** — проверка безотходного раскроя всей партии.
4. **Подбор длин** — MILP выбора каталожных длин с пределом +5% массы.
5. **Обрезка по внешнему контуру** (опционально) — физическое укорачивание.
6. **Обход отверстий** (опционально) — перенос прямых стержней.

Все этапы сохраняют исходный спрос, проверяют покрытие повторно и не ослабляют
инженерные правила.

## 7. Что показывается на сайте

### Основной режим (по умолчанию)

- **Цветные изополя** — исходная потребность из DXF.
- **Синие прямоугольники** — пятна потребности (`demand_bbox`).
- **Пунктир** — осевые огибающие наборов после 40d/раскроя (не граница AreaReinforcement).
- **Легенда** — уровни шкалы с цветами.
- **Таблица параметров** — диаметр, шаг, количество, размеры каждой зоны.

### Проверки (4 карточки)

| Проверка | Что означает |
|----------|-------------|
| Покрытие исходной потребности | Все ли КЭ покрыты в принятой модели |
| Раскрой прутка 11,7 м | Проходит ли безотходный раскрой всей партии |
| Границы и проёмы плиты | Проверено ли в переданной плоской модели host |
| Создание в Revit | Всегда «не проверено» — web не изменяет модель |

### Варианты раскладки

Переключатель «Вариант раскладки» меняет весь отчёт: схему, метрики, ведомость,
проверки и JSON. Каждый вариант — независимая комбинация решений четырёх направлений.

## 8. Передача в Revit

### «Изополя и зоны · JSON» (основной)

Формат `source-isofields-zones/v1`:
- все КЭ с цветом и уровнем;
- все зоны с `demand_bbox`, параметрами, огибающими;
- направление, диаметр, шаг, количество, размеры, координаты.

Используется:
- **SourceWorkflow** → «Разместить исходные зоны семействами» (на текущем плане);
- **SourceWorkflow** → «Создать 4 видов: изополя + зоны» (4 отдельных чертёжных вида).

### «Физическая раскладка · JSON» (дополнительно)

Формат `graphic-bar-plan-draft/v1` / `pruned` / `repaired`:
- физические стержни после обработки;
- новые длины, массы, отсечения;
- provenance (происхождение каждого стержня).

Используется:
- **Rebar Review** → создание native Rebar в Revit.

## 9. Честные ограничения

- **Не глобальный оптимум.** GA работает в пределах конечного CandidateSet.
- **Плоская модель.** Отверстия, защитный слой, перепады высоты не учитываются
  в основном сценарии.
- **40d — контрольная аппроксимация.** Не нормативный расчёт анкеровки.
- **Не заменяет конструктора.** Узлы, высоты, совместная укладка требуют
  инженерного решения.
- **Не автоматическая выдача.** Результат требует проверки и согласования.
- **Revit-интеграция диагностическая.** Плагин не сохраняет проект автоматически,
  не синхронизирует, не изменяет существующую арматуру.
