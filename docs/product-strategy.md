# Продуктовая стратегия: инженерный помощник, гейты и метрики

Статус: решение команды от **21 августа 2026 года**. Документ фиксирует продуктовый
смысл MVP поверх инженерной постановки из
[`optimization-notes.md`](optimization-notes.md) и официальных критериев из
[`mvp-gate-assessment-2026-08-21.md`](mvp-gate-assessment-2026-08-21.md).

## Зафиксированные решения

1. Критерии заказчика — обязательный контракт продукта, а не финальный чек-лист перед
   показом. Для каждого доступного требования интерфейс показывает факт, норматив,
   абсолютное и относительное отклонение.
2. Продукт позиционируется как **помощник конструктора**. Он предлагает проверенные
   варианты и объясняет отклонения, но не утверждает, что заменяет инженера, и не
   выпускает решение без явного выбора пользователя.
3. Новые простые deterministic-baseline и их ручной тюнинг замораживаются. Уже
   реализованные методы остаются контрольной группой. Следующая исследовательская ветка
   — генетический/эволюционный поиск по рекомендации научного руководителя, но каждый
   кандидат всё равно проходит общий repair и hard-валидатор.
4. К техническим метрикам добавляются продуктовые: скорость получения принятого
   черновика, объём ручной доработки, доля принятых рекомендаций и доверие пользователя.

## Пользователь и обещание продукта

Основной ЛПР и пользователь MVP — инженер-конструктор, отвечающий за безопасность,
оформление и выпуск рабочей документации. Его нельзя ставить перед чёрным ящиком с
кнопкой «сделать за меня».

Рабочая формулировка:

> Система разбирает исходные изополя, готовит несколько допустимых вариантов раскладки,
> проверяет измеримые правила и показывает цену каждого компромисса. Конструктор
> выбирает вариант, при необходимости корректирует его и только после этого передаёт в
> Revit.

Не использовать в интерфейсе обещания «автоматически спроектирует», «лучшее решение» или
«заменяет ручную работу». Допустимые формулировки: «рекомендуемый вариант», «черновик»,
«проверено по подключённым правилам», «требует решения конструктора».

## Целевой пользовательский сценарий

1. Конструктор загружает четыре DXF одной плиты и подтверждает распознанные направления,
   единицы и профиль А101.
2. Система показывает качество входа и перечисляет правила, которые пока нельзя
   проверить автоматически.
3. Оптимизатор строит общеплитный Парето-фронт; недопустимые варианты исключаются, но
   причины остаются видимыми.
4. Интерфейс предлагает объяснимую рекомендуемую точку и соседние альтернативы: легче,
   проще в монтаже или ближе к эталону.
5. Для каждого варианта показываются четыре направления, зоны, масса, стержни, runtime и
   отклонения от гейтов/инженерного эталона.
6. Конструктор выбирает вариант либо указывает причину отклонения/отказа. Ручной выбор
   считается штатным действием, а не ошибкой пользователя.
7. В Revit передаётся **черновик** с версией правил и полным протоколом проверок.
8. Плагин создаёт элементы в безопасной транзакции; инженер просматривает результат и
   отдельно подтверждает его для дальнейшего выпуска.

## Как показывать гейты

Для численного требования выводятся:

```text
факт · норматив · абсолютное отклонение · относительное отклонение, % · статус
```

Относительное отклонение считается как
`(факт - норматив) / норматив × 100%`. Если норматив равен нулю, процент математически
не определён: интерфейс показывает `—`, а не выдуманный процент.

Текущий web уже умеет оценить на уровне результата:

- 100% перекрытия требуемых КЭ;
- минимальную ширину зоны в КЭ;
- анкеровку с каждого конца в `d`;
- кратность ширины шагу для всех зон;
- число диагностированных коллизий/нарушений раздвижки;
- наличие всех четырёх направлений;
- для явно выбранной плиты нуля — отклонение массы и физических стержней от решения
  конструктора.

Проверка разрешённых позиций по таблицам А101 2.4.2–2.4.7 остаётся `не проверено` до
оцифровки каталога. Нельзя превращать отсутствие проверки в зелёный статус. Панель
описывает output-гейты выбранного варианта и не является процентом готовности всего MVP:
PNG, Revit и инструкция оцениваются отдельно.

## Метрики продукта

### Главная метрика

**Время конструктора до принятого безопасного черновика раскладки**, от загрузки
исходных данных до явного выбора варианта, прошедшего все подключённые hard-проверки.

Она одновременно отражает пользу автоматизации и не поощряет небезопасный выпуск.

### Инженерные guardrail-метрики

| Метрика | Цель MVP |
|---|---:|
| Скрыто недоармированные КЭ | 0 |
| Принятые запрещённые позиции А101 | 0 |
| Ошибки единиц м/мм | 0 |
| Изменённые плагином посторонние элементы Revit | 0 |
| Воспроизводимость при одинаковом seed/настройках | 100% для deterministic; фиксируемая для GA |

### Метрики ценности и принятия

| Метрика | Что показывает |
|---|---|
| Доля расчётов, где инженер выбрал один из предложенных вариантов | Полезность набора рекомендаций |
| Доля принятия рекомендованной точки | Качество default, но не обязанность пользователя согласиться |
| Медианное время до выбора и до Revit-черновика | Экономия рабочего времени |
| Число ручных правок зон/параметров после генерации | Реальный объём доработки |
| Причины отказа или выбора соседней точки | Данные для улучшения цели и будущей модели предпочтений |
| Масса после инженерской правки относительно эталона и первой рекомендации | Экономичность без отрыва от workflow |
| Число предупреждений на принятый вариант | Понятность и зрелость автоматических проверок |
| Успешность повторного расчёта/экспорта без помощи команды | Удобство и устойчивость |

На MVP данные можно сохранять в скачиваемый JSON/локальный журнал без БД. Сбор
персональной продуктовой аналитики и отправка наружу требуют отдельного согласования.

### Proxy монтажной сложности

По стенограмме научного консультанта вторая ось Парето-фронта должна отражать не
«количество прямоугольников само по себе», а трудность комплектации и монтажа. На первом
этапе нужно хранить компоненты раздельно:

- `zone_count` — сколько участков нужно прочитать и разместить;
- `physical_bar_count` — объём поштучной работы;
- число уникальных диаметров, шагов и длин — сложность снабжения/маркировки;
- число уникальных позиций после группировки — сложность спецификации;
- число ручных коррекций/предупреждений — измеренная последующая сложность.

В текущем коде до согласования формата спецификации используется честно названный
`unique_layout_signature_count`: уникальная комбинация
`направление × диаметр × шаг × установленная длина`. Это proxy, а не подтверждённое
число позиций PDF; число ручных коррекций появится после действий выбора/редактирования.

До инженерного исследования не склеивать их в одно число с произвольными весами. Для MVP
показывать прозрачный вектор метрик и дать конструктору выбор. Позже связать компоненты с
человеко-часами и стоимостью логистики на реальных проектах.

## Приоритет алгоритмического трека

1. Готово: зафиксировать общеплитный Парето-контракт, hard-revalidation и прозрачный
   вектор сложности; web позволяет выбрать вариант внутри текущего набора кандидатов.
2. Готово: воспроизводимый memetic GA использует elite seed frozen-baseline,
   `split/merge/shift/change-level/baseline-patch`, repair и фиксированный seed; UCB1
   адаптивно выбирает оператор, `uniform` остаётся контролем.
3. Далее: сравнить `uniform` и UCB1 при одинаковом числе evaluation и времени; на малых
   задачах сопоставлять с branch-and-bound/exact oracle, а не выдавать GA за гарантированный оптимум.
4. Выводить не название «ИИ», а измеримый эффект: массу, сложность, нарушения и
   отклонение от конструктора.
5. Накапливать решения инженеров и причины выбора. Регрессию/inverse optimization для
   default-точки запускать только после появления реальных plate-level меток.

Первый исследовательский scalar-ranker уже запущен на трёх слабых plate-level метках:
LOPO top-1 `2/3`, top-3 `3/3`, но mass-gate top-1 только `2/3`. Поэтому его допустимый
продуктовый режим — подсветить три варианта и объяснить вес `0,75`, а не нажать
«Сформировать» без подтверждения конструктора. Выбор/отказ пользователя должен стать
следующей, более качественной меткой.

Online AOS для операторов реализован без датасета и не заменяет оптимизатор. ML/LLM для
предпочтений, подписей и оформления остаются возможными бонусами после появления данных.

Жёсткие правила не входят в fitness как мягкие штрафы, которые можно «выкупить» хорошей
массой. Repair либо устраняет нарушение, либо кандидат исключается.
