# Подключение рабочей плиты и сдвиг остатка длины

## Что реализовано

Ответ Full Plate Trial 0.6.0 теперь можно напрямую подготовить для полного
четырёхнаправленного расчёта. Существующий ZIP специалисту **менять не нужно**.
Поддерживается и ожидаемый `blocked_setup` после отмены выбора типов: ошибку
создания не путаем с неполным чтением геометрии. `read_issues` должны быть пустыми.
При состоявшемся создании требуется подтверждённый откат; Pending и неуспешное
восстановление модели отклоняются.

Новый формат `qmonitoring-host-input/v1` хранит проверяемый снимок, SHA256
исходного отчёта и явный сдвиг XY. Система координат: **Revit = DXF + сдвиг**.
В систему DXF переводится host, исходные КЭ не перемещаются и не удаляются.
Высоты остаются относительно реальных граней; Z из DXF за грань плиты не принимается.
Ни нулевой сдвиг, ни поворот, ни масштаб не угадываются.

В отличие от прежнего Reference Probe, проверяются не только верх/низ:
все сериализованные боковые грани, стенки каждого проёма, нормали, длины рёбер
и объём Solid должны совпасть с одной прямоугольной призмой и её сквозными
прямоугольными отверстиями. Дополнительные полости, уступы, дуги, наклонные
грани и неизвестная геометрия не заменяются bbox. Это проверка полученного
снимка, не подтверждение актуальности открытой модели и не инженерное разрешение.

## Команды после получения JSON

```bash
PYTHONPATH=src python scripts/prepare_working_host.py \
  --report /path/to/qmonitoring-full-plate.json \
  --offset-x-mm X --offset-y-mm Y \
  --output artifacts/working-host.json
```

`X` и `Y` — подтверждённые числовые сдвиги, не значения по умолчанию.
В существующей команде четырёх DXF используется
`--host-input artifacts/working-host.json` вместо `--reference ... --confirm-host-xy`.
Остальные явные SHK, фазы, класс, ограничения и бюджет не меняются автоматически.
Старый Reference-сценарий сохранён отдельно, без подмены схемы отчёта.
CLI принимает ограниченный UTF-8 JSON, запрещает повторные ключи/NaN и перезапись.

## Проверенная гипотеза: остаток длины можно распределить несимметрично

Раньше дополнительная длина после округления к каталогу раскроя всегда
распределялась поровну. Это могло вывести стержень за грань даже тогда, когда
он помещается целиком с исходной анкеровкой.

Пусть продольная потребность занимает `[a,b]`, требуемая анкеровка каждого конца
равна `e=40d`, установленная длина — `L`, допустимый продольный интервал
host с cover — `[h0,h1]`. Допустимые начала стержня:

`max(h0, b+e−L) ≤ start ≤ min(h1−L, a−e)`.

Из этого интервала выбирается положение, ближайшее к первоначальному. Проёмы
дополнительно исключают положения, в которых хотя бы один физический стержень
компонента заходит в отверстие с защитным слоем. Если положений нет — ошибка,
не обрезка. `demand_bbox`, диаметры, фазы, количество и установленная длина
не меняются. Каждый конец независимо сохраняет не менее полных 40d.

Обычный конструктор по-прежнему создаёт центрированную зону. Дополнительный
сервис применяется только при заданном host; общий независимый валидатор
проверяет фактическую длину и анкеровку обоих концов вместо требования симметрии.
Публичные поля `models.py` и схема `reinforcement-zone-revit/v2` не изменялись.
Метрики и экспорт используют фактический продольный интервал.

В полном поиске минимальное поперечное окно заранее помещается в допустимую
область host. Оно перемещается целиком, сохраняя весь спрос и обслуживающие оси.
После увеличения длин для безотходного раскроя подгонка и общая проверка
повторяются. Проверки столкновений/фаз/высот этим не отменяются.

## Эксперименты и выводы

Контрольный пример для X/Y, верх/низ: стержень Ø18 длиной 5850 мм и исходным
интервалом `[-975,4875]` сдвигается на 200 мм в `[-775,5075]`. Потребность
`[0,3900]` и минимум 720 мм с каждого конца сохранены. Выход за край исчезает,
масса и количество не изменяются. Отдельный пример со сквозным проёмом проходит
после сдвига целого набора на 50 мм. Недостаточная анкеровка и отверстие внутри
обязательного участка дают отказ.

На реальном полном кандидате №10 из `real-full-1024-batch-verified.json`
получен **отрицательный результат гипотезы**:

| Направление | Стержни вне TEST_SLAB_01 до | После | Зоны, для которых сдвига недостаточно |
| --- | ---: | ---: | ---: |
| Низ X | 151 | 151 | 5 |
| Низ Y | 277 | 277 | 14 |
| Верх X | 337 | 337 | 9 |
| Верх Y | 225 | 225 | 12 |
| Всего | **990** | **990** | **40** |

Все 108 зон, 2531 стержень и 37 942,993252125 кг сохранены. Неисправленные зоны
не удалялись. Покрытие по исходному исследовательскому профилю до/после одинаково.
Результат: `artifacts/host_fit_2026_09_13/real-stock-fit.json`.
Воспроизведение — `scripts/experiment_host_stock_fit.py` с явными анализом,
Reference JSON, корнем исходников, индексом кандидата и подтверждением XY.
DXF/SHK подбираются по исходному имени **и SHA256**, не только по имени.

Повтор полного расчёта с известным host, строгими 40d и пулом 128 сохраняет
все 2132 КЭ каждого направления, но не выдаёт ни одной полной раскладки:
продольное необходимое условие нарушено для 13 / 66 / 67 / 60 КЭ. Решатель
не запускается для заведомо несовместимой задачи. Результат:
`artifacts/host_fit_2026_09_13/real-full-host-aware.json`.

Это **не доказательство невозможности армировать рабочий фундамент**:
TEST_SLAB_01 толщиной 300 мм — стенд, а не проверенный эквивалент рабочей RVT.
Гипотеза устраняет ошибочные отказы от центрирования остатка, но не разрешает
реальную задачу края и не заменяет расчёт анкеровки/потребности по СТО.

## Проверка

Полный набор: **1408 passed**, три известных предупреждения openpyxl о
колонтитулах. Затем отдельно пройдены **34 новых теста**, включая подготовку
host из JSON, полный сценарий четырёх DXF, контроль проёмов/граней/объёма,
сдвиг без изменения метрик, CLI/SHA256/запрет перезаписи и воспроизводимый
эксперимент. Новый pyRevit-код в этой итерации не менялся; это не Windows-приёмка.
