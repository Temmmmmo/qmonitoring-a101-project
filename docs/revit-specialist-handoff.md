# Передача текущего состояния Revit-специалисту

Привет! Расскажу, что у нас сейчас готово, чтобы ты мог посмотреть и предложить, как
лучше встроить результат в Revit.

Мы делаем систему автоматической раскладки зон дополнительного армирования плиты по
мозаике изополей ЛИРА-САПР.

Репозиторий:
[Temmmmmo/qmonitoring-a101-project](https://github.com/Temmmmmo/qmonitoring-a101-project)

Сейчас алгоритмическая часть написана на Python и работает следующим образом:

```text
DXF из ЛИРА-САПР
        ↓
распознавание мозаики и цветовой шкалы
        ↓
карта требуемого армирования
        ↓
алгоритмы разбиения на прямоугольные зоны
        ↓
постобработка и инженерная проверка
        ↓
LayoutSolution с координатами и параметрами зон
```

## Что уже работает

- загрузка DXF с мозаикой изополей;
- автоматическое определение направления по имени файла:
  - нижняя X;
  - нижняя Y;
  - верхняя X;
  - верхняя Y;
- нормализация метров и миллиметров;
- распознавание КЭ и цветовой шкалы;
- сопоставление цвета с требуемым диаметром и шагом арматуры;
- несколько переключаемых алгоритмов раскладки;
- построение прямоугольных зон;
- расчёт ширины, длины, анкеровки `40d`, диаметра, шага, количества стержней и массы;
- проверка, что требуемое армирование полностью покрыто;
- сбор четырёх уникальных направлений в общий `PlateSolution` с суммарными метриками и
  plate-level статусом;
- web-интерфейс, в котором можно загрузить один DXF либо комплект из четырёх, выбрать
  алгоритмы и посмотреть общий результат с отдельными схемами направлений;
- Docker-сборка и серверная версия.

Одна выходная `LayoutZone` — это не отдельный стержень, а прямоугольное поле
дополнительного армирования. Сейчас для каждой зоны доступны примерно такие данные:

```text
id
направление X/Y
слой верх/низ
координаты прямоугольника
координаты исходной требуемой области
ширина зоны
требуемая длина
длина с 40d
принятая длина стержня
диаметр
шаг
количество стержней
положение первой оси
масса
покрытые КЭ
диагностика
```

Все координаты и размеры внутри Python-ядра хранятся в миллиметрах. Координаты пока
остаются в системе исходного DXF.

## Важные правила

- в research-профиле прямоугольные зоны могут пересекаться; это ещё нужно подтвердить
  с конструктором/технологом до production-экспорта;
- `40d` и раздвижка стержней применяются после построения логических зон;
- недоармирование считается ошибкой;
- алгоритмы не должны самостоятельно создавать геометрию Revit;
- предполагается, что Revit-часть получит готовые параметры зон и отобразит их через
  подходящие семейства.

Python-ядро и web уже умеют собирать четыре направления плиты. Следующий интеграционный
этап — зафиксировать согласованный с Revit-плагином `PlateSolution` JSON и добавить его
выгрузку/передачу без дублирования инженерной логики.

## Пока не готово

- Revit-плагин;
- окончательный JSON-контракт для Revit;
- общеплитный Парето-фронт и выбор «Точки 3»;
- автоматическое размещение зон и аннотаций на виде;
- привязка DXF-координат к координатам Revit;
- окончательный мэппинг семейств и параметров;
- PNG-ingest.

Предварительно мы видим интеграцию так:

```text
Revit-плагин
    ↓
передаёт DXF и настройки в Python API
    ↓
получает PlateSolution JSON
    ↓
размещает семейства зон и заполняет параметры
```

Но не хотим заранее навязывать этот вариант. Посмотри, пожалуйста, на текущую модель и
подумай:

- каким элементом Revit правильнее представлять одну `LayoutZone`;
- можно ли использовать существующие семейства и какие параметры им нужны;
- как надёжнее совместить координаты DXF с координатами вида Revit;
- лучше ли плагину обращаться к API или импортировать готовый JSON;
- какие данные Python должен обязательно передавать;
- как удобнее организовать четыре направления;
- какой минимальный сквозной сценарий реально собрать до конца августа.

От нас можем быстро предоставить пример DXF, пример результата JSON, тестовую раскладку
инженера и доступ к работающему web/API. После твоего предложения зафиксируем контракт
между Python и Revit и постараемся не менять его без необходимости.
