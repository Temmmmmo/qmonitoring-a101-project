# Архитектура оптимизации

Статус: MVP-контракт, обновлённый после встречи 2026-08-20. Инженерные допущения и открытые вопросы находятся в
[`optimization-notes.md`](optimization-notes.md).

Повторная сверка геометрии зон с готовыми КЖ выявила необходимость отделить логические
прямоугольники от осей стержней и установленной длины. После встречи overlap зон
разрешён, а `40d`/раздвижка оформлены как общая постобработка. Обоснование, локальные
источники и оставшиеся допущения описаны в
[`layout-research-2026-08-19.md`](layout-research-2026-08-19.md).

Обзор всех реализованных методов, их пошаговой работы и Mermaid-схемы проекта находятся
в [`algorithms.md`](algorithms.md).

## Главный принцип

Парсер и оптимизаторы не зависят друг от друга напрямую:

```text
DXF -> Mosaic -> mapping? -> адаптер -> LayoutProblem -> LayoutOptimizer -> demand zones
                                                       ↓
                 общая постобработка + validator -> LayoutZone[] -> LayoutSolution
                                                                    ↓
                                                               JSON/Revit
```

- `Mosaic` — стабильный публичный контракт результата ingest;
- `mapping` — отдельное обогащение `Band` для DXF без `.shk`, только по явно выбранной
  и проверенной таблице;
- `LayoutProblem` — единый вход всех алгоритмов;
- `LayoutSolution` — единый выход для валидации, JSON и HTML;
- алгоритм выбирается по стабильному имени через `OptimizerRegistry`;
- масса после `40d`/раздвижки, покрытие и нарушения пересчитываются общим
  `evaluate_layout`, а не самим
  алгоритмом. Поэтому результаты можно сравнивать на одинаковых правилах.

Глобальный оптимизатор выбирает прямоугольные зоны, потому что это прямо требуемый ТЗ
результат. Внутренняя целевая функция пока штрафует число зон; соответствие этого
счётчика слову «деталь» на графике ТЗ требует подтверждения. Для каждой зоны общие
сервисы постобработки вычисляют ширину, длину с `40d`, диаметр, шаг, фазу, количество
стержней и итоговую массу.
Revit-плагин затем размещает выбранное семейство по этим параметрам.

```text
  mappings/

    phase.py         подбор общей фазы и устранение физических конфликтов
  algorithms/
    base.py          протокол LayoutOptimizer
    _guillotine.py   общая генерация допустимых ортогональных разрезов
    bbox.py          одна сильная охватывающая деталь — грубый baseline
    bsp.py           рекурсивное ортогональное разбиение — baseline
    greedy.py        жадное объединение поперечных полос — быстрый baseline
    greedy_priority.py  разрезы с приоритетом дорогих цветовых уровней
    agglomerative.py  bottom-up слияние связных пятен уровней
    row_run_greedy.py жадное объединение продольных профилей спроса
    strip_profile_dp.py DP по последовательным поперечным полосам
    spatial_partition_greedy.py сеточная маска и укрупнение непересекающихся зон

      operators.py   split/merge/shift/change-level/baseline-patch

src/rebar/golden/

  zone_schedule.py   стабильные марки и выноски параметрических зон
src/rebar/application/

```

`src/rebar/optimization/__init__.py` — единственная рекомендуемая точка импорта для
потребителей. Внутреннюю структуру можно менять без переписывания CLI и отчёта.

Локальная визуализация вынесена из оптимизации в `src/rebar/reporting/`, а исполняемый
CLI остаётся тонким файлом `scripts/compare_optimizers.py`.

Локальный web-MVP использует ту же границу:

```text
POST /api/analyze
       ↓
application.analyze_direction
       ↓
DXF ingest -> mapping? -> LayoutProblem -> OptimizerRegistry -> LayoutSolution[]
                                                               ↓
                                      standards validation -> reporting / export
```

`src/rebar/application/` оркестрирует один use case, но не содержит геометрических
правил. `src/rebar/web/` отвечает только за временный upload, HTTP-валидацию,
сериализацию и UI. Поэтому будущие CLI, публичный API и Revit-интеграция смогут вызывать
тот же сценарий без копирования алгоритмов. Встроенный demo-case создаётся как настоящий
синтетический DXF в `application/demo.py` и проходит тот же путь. Загруженные web-файлы
сейчас не сохраняются.

`application/revit_export.py` является отдельной выходной границей: он принимает уже
выбранный и проверенный `PlateSolution`, добавляет ведомость марок и создаёт компактный
`plate-solution-revit/v1` без web-SVG и остальных кандидатов. Пока safety-гейты не
закрыты, контракт остаётся `draft` и не выдаёт решение за готовое к применению.

`src/rebar/standards/` хранит версионированную транскрипцию таблиц А101 отдельно от
mapping и алгоритмов. Mapping выбирает профиль и переносит его ID в `DemandMap.meta`;
общий `evaluate_layout()` запрещает явно красные позиции после генерации кандидата.
Application-слой тем же валидатором формирует гейт `pass/fail/not_checked`, поэтому
эвристика не может обойти каталог собственной оценкой допустимости.

`src/rebar/learning/preference.py` расположен после Pareto/hard-validation. Он принимает
только метрики допустимых `PlateCandidate`, учит один вес ранжирования и не может
создавать зоны или менять инженерные ограничения. JSON/HTML этого эксперимента остаётся
в `reporting/preference_calibration.py`.

## Контракт алгоритма

Каждая реализация обязана иметь стабильное `name` и один метод:

```python
def solve(
    self,
    problem: LayoutProblem,
    request: AlgorithmRequest | None = None,
) -> LayoutSolution:
    ...
```

Алгоритм отвечает только за выбор разбиения. Он должен использовать общую детализацию и
не должен подменять правила оценки локальной формулой ради более выгодных метрик.

Метод, который естественно создаёт популяцию вариантов, дополнительно реализует:

```python
def solve_many(
    self,
    problem: LayoutProblem,
    request: AlgorithmRequest | None = None,
) -> tuple[LayoutSolution, ...]:
    ...
```

Это контракт `LayoutCandidateGenerator`. Application-слой сохраняет один центральный
представитель для обратной совместимости, но передаёт всю серию общему hard-валидатору
и Парето-фильтру. `genetic-pareto` является первой такой реализацией.

Текущий выходной контракт остаётся на уровне зоны:

```python
@dataclass(frozen=True)
class LayoutZone:
    id: str
    bbox: BBox
    demand_bbox: BBox
    level_index: int
    rebar: Rebar
    width_mm: float
    required_length_mm: float
    anchored_length_mm: float
    installed_length_mm: float
    first_bar_coordinate_mm: float
    bar_count: int
    mass_kg: float
```

При `width_mm = k × step` количество равно `k + 1`, а масса считается по одинаковой
`installed_length_mm` всех стержней зоны. Область спроса, минимальная длина с анкеровкой,
принятая длина отрезка и первая поперечная ось разделены явно. Линии отдельных стержней
вычисляются как `first + i × step`; отдельный публичный `PlacedBar[]` не нужен.

## Уровни решения и метрик

Текущий `LayoutProblem -> LayoutSolution` описывает **одно направление** армирования.
Его `metrics.detail_count` исторически равен числу `LayoutZone`, а не числу стержней
внутри них. В интерфейсе эту величину следует называть `zone_count`, пока терминология
графика ТЗ не подтверждена.

Для любой раскладки уже можно вычислить второй показатель без нового доменного типа:

```text
physical_bar_count = sum(zone.bar_count for zone in solution.zones)
```

Число позиций спецификации требует отдельной группировки стержней по геометрии,
диаметру и длине. Оно не равно автоматически ни числу зон, ни числу стержней.

На встрече подтверждено, что график «Точка 3» агрегирует четыре направления. Поэтому для
полного сценария нужен следующий слой в пакете оптимизации:

```text
PlateProblem
├── bottom-X: LayoutProblem
├── bottom-Y: LayoutProblem
├── top-X:    LayoutProblem
└── top-Y:    LayoutProblem

PlateSolution
├── direction_solutions: 4 × PlateDirectionSolution(direction + LayoutSolution)
├── zone_count: sum(direction.detail_count)
├── physical_bar_count: sum(zone.bar_count)
├── total_mass_kg: sum(direction.total_mass_kg)
└── diagnostics/status
```

Базовые контракты реализованы в `optimization/contracts/plate.py`; общая агрегация и
распространение невалидности любого направления находятся в
`optimization/services/plate.py`. `application/analyze_plate.py` принимает ровно четыре
источника, проверяет уникальность направлений и строит по одному общеплитному baseline
на каждый выбранный алгоритм. Публичный ingest-контракт `models.py` не менялся.
Web-граница может передать каждому `PlateDirectionSource` один и тот же явно загруженный
`.shk`; `read_mosaic` всё равно независимо проверяет число полос каждого DXF. При
несовместимости весь plate-запуск отклоняется до построения фронта.

Слой конечных кандидатов реализован отдельно:

```text
LayoutSolution[] × 4
  -> evaluate_layout() повторно для каждого кандидата
  -> DirectionParetoFront × 4
  -> комбинации разных алгоритмов по направлениям
  -> PlateSolution[]
  -> PlateParetoFront(mass, explicit complexity axis)
```

Контракты находятся в `optimization/contracts/front.py`, прозрачные метрики — в
`services/constructability.py`, Pareto-pruning — в `services/pareto.py`. Недопустимый
статус или ошибка hard-валидатора исключают вариант до сравнения. Равные точки
схлопываются с сохранением идентификаторов альтернатив. Сейчас источники дают по одному
финальному решению на алгоритм, поэтому этот фронт честный внутри переданного конечного
набора, но не является доказанным глобальным фронтом.

Геометрические задачи четырёх направлений решаются независимо. Каждый кандидат обязан
сохранять `zone_count`, `physical_bar_count` и `total_mass_kg` отдельно. Для построения
общего фронта выбирается явная метрика сложности: сейчас `zone_count` или
`physical_bar_count`. Дополнительно сохраняются уникальные диаметры, шаги, установленные
длины, сигнатуры раскладки и число предупреждений. Веса для этих компонентов не
придумываются. До подтверждения терминологии графика нельзя молча называть
`detail_count` числом деталей заказчика.

`AlgorithmRequest.max_details` сейчас относится только к одному `LayoutSolution`.
Значение `4` в примере README — ручной smoke-test, а не найденная «Точка 3» и не итог
всей плиты.

Чтобы добавить следующий алгоритм, например `cpsat`:

1. создать отдельный файл `optimization/algorithms/cpsat.py`;
2. реализовать протокол без изменения `Mosaic` и существующих контрактов;
3. зарегистрировать класс в `built_in_optimizer_registry()`;
4. добавить общий поведенческий тест в `tests/optimization/test_algorithms.py`;
5. после этого имя автоматически можно передать в локальный отчёт через `--algorithms`.

Генетический оптимизатор реализован публичным `genetic_pareto.py` и внутренним пакетом
`algorithms/genetic/`. Хромосома выбирает прямоугольники из пространственного
CandidateSet, дополненного геометриями сильных frozen-baseline. UCB1 адаптивно выбирает
один из фиксированных предметных операторов, но crossover/mutation не получают
права создавать непроверенный инженерный результат: после них обязательны
детерминированный repair, общая постобработка и `evaluate_layout`.

До любого оптимизатора application-слой вызывает `apply_single_cell_rule()`. Сервис
возвращает новый `LayoutProblem`, не изменяет `Mosaic` и кладёт полный протокол понижений
в `problem.meta`. Там же `resolve_zone_count_limit()` заменяет отсутствующий cap на
естественный максимум: `1..число всех КЭ` для непустого спроса и `0..0` для пустого.
Внешний Парето-фильтр для двух целей работает после сортировки за `O(n log n)`, поэтому
общеплитное произведение кандидатов больше не попадает в квадратичный dominance-loop.

ML выбора «Точки 3» находится над `PlateSolution`, а не внутри геометрического
валидатора. Локально доступно 11 объединённых инженерских выдач и 0 явно размеченных
точек колена, поэтому первая модель должна оценивать один параметр предпочтения и
проверяться leave-one-project-out.

## Текущие ограничения MVP

`bbox`, `bsp`, `greedy`, `greedy-priority`, `agglomerative`, `row-run-greedy`,
`strip-profile-dp`, `spatial-partition-greedy` и `genetic-pareto` — сравнимые
экспериментальные методы, а не готовая инженерная выдача. Последний строит приближённый
многоточечный фронт внутри конечного CandidateSet и не заявляет глобальный оптимум.
Greedy сначала строит непересекающиеся поперечные полосы минимальной ширины, затем
объединяет соседние пары с наименьшим приростом целевой стоимости. Он быстрый и всегда
покрывает спрос в текущей модели, но не рассматривает произвольные прямоугольники и не
гарантирует глобальный оптимум.

`greedy-priority` использует те же допустимые гильотинные разрезы, что и BSP, но оценивает
их не только по немедленному снижению целевой функции. Дополнительный приоритет равен
оценке массы перерасхода, которую удаётся убрать, если сильный уровень больше не
назначается слабым КЭ. Вес задаётся `AlgorithmRequest.params["priority_weight"]`, по
умолчанию `1.0`. Это помогает изолировать дорогие уровни, но не снимает минимальную
ширину и обязательную общую постобработку.

`agglomerative` идёт в обратную сторону: начинает со связных по bbox пятен одного уровня
и сливает ближайшие зоны. Сначала устраняются обязательные конфликты, затем число зон
доводится до `max_details`. Это быстрый bottom-up baseline; связь через bbox и выбор
ближайшей пары являются эвристиками.

`spatial-partition-greedy` принципиально не группирует произвольные КЭ перед построением
bbox. Он дискретизирует область с шагом порядка медианного размера КЭ, строит
непересекающиеся начальные прямоугольники и затем укрупняет ортогональных соседей.
Слияние разрешено, только если весь новый сеточный bbox состоит из плиток с геометрией
`KLEENKA`; частично пересекающиеся активные зоны замыкаются в один прямоугольник.
Решение хранит полную жадную траекторию и недоминируемые точки внутри неё. Это создаёт
реальное множество вариантов для MVP, но не доказывает глобальную оптимальность и
зависит от разрешения сетки.

Общие ограничения baseline:

- минимальная ширина оценивается как `min_width_cells × медианный поперечный размер КЭ`;
- используется безопасная рабочая семантика: одна деталь должна быть не слабее каждого
  накрытого ею требуемого КЭ;
- для одинакового шага проверяется точный зазор на величину шага; для разных шагов
  валидатор до ответа конструктора консервативно требует больший шаг и предупреждает об
  использованном допущении;
- spatial baseline аппроксимирует разрешённую область плитками, пересекающими геометрию
  `KLEENKA`; точный векторный контур и семантика колонн/капителей пока отсутствуют;
- для произвольного DXF без `.shk` и без явно выбранной таблицы неизвестны диаметр и
  шаг, поэтому `DemandMap` построить можно, а `LayoutProblem` для детализации — нельзя;
- для четырёх DXF плиты нуля доступна таблица `plate-zero-d12-v1`; она проверяет шесть
  границ шкалы, связывает ACI по порядку и помечает результат как `mvp_assumption`.

Общий builder/postprocessor приводит ширину к `k × step`, вычисляет `bar_count = k + 1`,
применяет политику анкеровки, раздвижки и раскроя. `build_zone(cell_ids)` сохранён для старых baseline, а
`build_zone_from_bbox()` принимает пространственный прямоугольник без обратного
превращения в bbox группы КЭ. Независимый hard-валидатор разрешает overlap
`demand_bbox` зон одного направления, считает площадь объединения без двойного зачёта и
разрешает покрыть один КЭ объединением нескольких прямоугольников, каждый из которых
имеет достаточный уровень. Отдельный этап детализации разворачивает зоны в реальные
линии, добавляет `40d` и пытается обеспечить зазор крайних осей. Его предупреждения не
заставляют алгоритм склеивать прямоугольники.

## Реализованный этап физической модели

Перед solver и уровнем всей плиты общая физическая модель была исправлена:

1. отделить область спроса, установленный продольный интервал и поперечные оси;
2. сделать `40d` заменяемой политикой и добавить проектный каталог длин;
3. разрешить overlap `demand_bbox`, не допускать двойной зачёт площади и отдельно
   диагностировать совпадения стержней/крайних осей;
4. независимо пересчитывать покрытие, длину и массу;
5. покрыть правила синтетическими тестами X/Y и регрессией реального DXF;
6. добавить `row-run-greedy` и `strip-profile-dp` как два простых MVP-алгоритма;
7. рисовать в SVG как envelope зон, так и реальные линии стержней.

Все семь пунктов реализованы и покрыты общими поведенческими и синтетическими X/Y-тестами.
После MVP можно возвращаться к `PlateProblem`/`PlateSolution`, полному `CandidateSet`,
Парето-фронту и CP-SAT/MILP. Все методы сохраняют прежнюю границу `LayoutOptimizer` и
проходят один общий валидатор.

Внешняя проверка алгоритма не входит в оптимизатор. Пакет `golden` извлекает из готового
PDF плиты нуля 79 позиций, 1019 физических стержней и 3177,64 кг, а reporting строит
отдельный автономный HTML. После конвертации DWG→DXF eval-харнесс добавит сравнение bbox
и IoU, не меняя интерфейс алгоритмов. Подробности: [`golden-case.md`](golden-case.md).
