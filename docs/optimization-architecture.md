# Архитектура оптимизации

Статус: MVP-контракт от 2026-08-18. Инженерные допущения и открытые вопросы находятся в
[`optimization-notes.md`](optimization-notes.md).

## Главный принцип

Парсер и оптимизаторы не зависят друг от друга напрямую:

```text
DXF -> Mosaic -> адаптер -> LayoutProblem -> LayoutOptimizer -> LayoutZone[]
                                              ↓                 ↑ reject
                                           detailer -> PlacedBar[]
                                              ↓
                                           validator -> LayoutSolution
```

- `Mosaic` — стабильный публичный контракт результата ingest;
- `LayoutProblem` — единый вход всех алгоритмов;
- `LayoutSolution` — единый выход для валидации, JSON и HTML;
- алгоритм выбирается по стабильному имени через `OptimizerRegistry`;
- масса, покрытие и нарушения пересчитываются общим `evaluate_layout`, а не самим
  алгоритмом. Поэтому результаты можно сравнивать на одинаковых правилах.

Глобальный оптимизатор выбирает прямоугольные зоны, потому что они являются естественными
монтируемыми деталями и именно их количество входит в целевую функцию. Он не получает
права игнорировать стержни: общий detailer должен развернуть каждую зону в `PlacedBar[]`,
а validator — отклонить комбинацию зон, которую нельзя корректно детализировать.

## Структура пакета

```text
src/rebar/optimization/
  contracts/
    problem.py       DemandMap, ограничения и LayoutProblem
    result.py        запрос, детали, метрики и LayoutSolution
  adapters/
    mosaic.py        Mosaic -> DemandMap -> LayoutProblem
  services/
    geometry.py      чистые геометрические примитивы
    detailing.py     сейчас: предварительные анкеровка, число стержней и масса
    evaluation.py    сейчас: независимая проверка зон, покрытия и метрик
  algorithms/
    base.py          протокол LayoutOptimizer
    bbox.py          одна сильная охватывающая деталь — грубый baseline
    bsp.py           рекурсивное ортогональное разбиение — baseline
  registry.py        явная регистрация и выбор алгоритма
```

`src/rebar/optimization/__init__.py` — единственная рекомендуемая точка импорта для
потребителей. Внутреннюю структуру можно менять без переписывания CLI и отчёта.

Локальная визуализация вынесена из оптимизации в `src/rebar/reporting/`, а исполняемый
CLI остаётся тонким файлом `scripts/compare_optimizers.py`.

## Контракт алгоритма

Каждая реализация обязана иметь стабильное `name` и один метод:

```python
def solve(
    self,
    problem: LayoutProblem,
    request: AlgorithmRequest | None = None,
) -> LayoutSolution:
    ...
```

Алгоритм отвечает только за выбор разбиения. Он должен использовать общую детализацию и
не должен подменять правила оценки локальной формулой ради более выгодных метрик.

Целевой контракт детализации:

```python
@dataclass(frozen=True)
class PlacedBar:
    id: str
    start: Point
    end: Point
    diameter_mm: int


def detail_zone(problem: LayoutProblem, zone: LayoutZone) -> tuple[PlacedBar, ...]:
    ...
```

`LayoutSolution` должен содержать или сами `PlacedBar`, или однозначное параметрическое
представление, из которого они восстанавливаются без новых инженерных решений. Для
локального MVP предпочтительно сохранять явные стержни: их можно визуально проверить до
интеграции с Revit.

Стоимость зоны должна вычисляться как сумма масс созданных стержней. Предварительная
формула `bar_count × installed_length × удельная масса` допустима только если её результат
совпадает с явной детализацией.

Чтобы добавить `greedy` или `cpsat`:

1. создать отдельный файл `optimization/algorithms/greedy.py` или `cpsat.py`;
2. реализовать протокол без изменения `Mosaic` и существующих контрактов;
3. зарегистрировать класс в `built_in_optimizer_registry()`;
4. добавить общий поведенческий тест в `tests/optimization/test_algorithms.py`;
5. после этого имя автоматически можно передать в локальный отчёт через `--algorithms`.

## Текущие ограничения MVP

`bbox` и `bsp` — сравнимые baseline, а не готовая инженерная выдача:

- покрытие КЭ пока проверяется по попаданию центроида в прямоугольник;
- минимальная ширина оценивается как `min_width_cells × медианный поперечный размер КЭ`;
- используется безопасная рабочая семантика: одна деталь должна быть не слабее каждого
  накрытого ею требуемого КЭ;
- пересечения по умолчанию запрещены, но окончательное правило ещё ждёт ответа инженера;
- индивидуальные `PlacedBar` пока не создаются и не показываются в SVG;
- `bar_count`, длина и масса сейчас вычисляются формулой, а не по списку стержней;
- контуры проёмов и запрещённых областей пока отсутствуют во входном контракте;
- для DXF без `.shk` неизвестны диаметр и шаг, поэтому `DemandMap` построить можно, а
  `LayoutProblem` для детализации — нельзя.

Эти допущения сохраняются в `meta` результата и показываются в HTML. Следующий шаг —
заменять их подтверждёнными правилами внутри `services/`, не размножая разные трактовки
по алгоритмам.

## Следующий обязательный этап

До добавления CP-SAT/MILP и дальнейшего улучшения BSP нужно:

1. добавить `PlacedBar` в выходной контракт оптимизации;
2. реализовать одинаковую для всех алгоритмов раскладку X- и Y-стержней внутри зоны;
3. обеспечить шаг, анкеровку `40d` и согласованность `bar_count`;
4. запретить пересекающиеся зоны одного направления либо доказать допустимость через
   разведённые стержни;
5. считать коллизии и массу по фактическим стержням;
6. рисовать зоны полупрозрачно, стержни — отдельными линиями, нарушения — красным;
7. покрыть синтетическими тестами координаты, шаг, анкеровку, X/Y и коллизии, затем
   проверить результат на реальном DXF.

Для следующей реализации до подтверждения инженером принимаем безопасные допущения:
положительное пересечение зон одного направления запрещено; шаг трактуется как максимально
допустимый; стержни раскладываются симметрично. Эти допущения должны быть явно отмечены в
отчёте и легко заменяться настройками после уточнения ТЗ.
