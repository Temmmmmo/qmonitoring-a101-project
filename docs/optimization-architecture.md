# Архитектура оптимизации

Статус: MVP-контракт от 2026-08-18. Инженерные допущения и открытые вопросы находятся в
[`optimization-notes.md`](optimization-notes.md).

Обзор всех реализованных методов, их пошаговой работы и Mermaid-схемы проекта находятся
в [`algorithms.md`](algorithms.md).

## Главный принцип

Парсер и оптимизаторы не зависят друг от друга напрямую:

```text
DXF -> Mosaic -> адаптер -> LayoutProblem -> LayoutOptimizer -> LayoutZone[]
                                              ↓
                  общий расчёт параметров + validator -> LayoutSolution -> JSON/Revit
```

- `Mosaic` — стабильный публичный контракт результата ingest;
- `LayoutProblem` — единый вход всех алгоритмов;
- `LayoutSolution` — единый выход для валидации, JSON и HTML;
- алгоритм выбирается по стабильному имени через `OptimizerRegistry`;
- масса, покрытие и нарушения пересчитываются общим `evaluate_layout`, а не самим
  алгоритмом. Поэтому результаты можно сравнивать на одинаковых правилах.

Глобальный оптимизатор выбирает прямоугольные зоны, потому что это прямо требуемый ТЗ
результат и именно их количество входит в целевую функцию. Для каждой зоны общие сервисы
вычисляют ширину, длину с `40d`, диаметр, шаг, количество стержней и массу. Revit-плагин
затем размещает выбранное семейство по этим параметрам.

## Структура пакета

```text
src/rebar/optimization/
  contracts/
    problem.py       DemandMap, ограничения и LayoutProblem
    result.py        запрос, детали, метрики и LayoutSolution
  adapters/
    mosaic.py        Mosaic -> DemandMap -> LayoutProblem
  services/
    geometry.py      чистые геометрические примитивы
    detailing.py     ширина, анкеровка, число стержней и масса зоны
    evaluation.py    независимая проверка зон, покрытия, зазоров и метрик
  algorithms/
    base.py          протокол LayoutOptimizer
    _guillotine.py   общая генерация допустимых ортогональных разрезов
    bbox.py          одна сильная охватывающая деталь — грубый baseline
    bsp.py           рекурсивное ортогональное разбиение — baseline
    greedy.py        жадное объединение поперечных полос — быстрый baseline
    greedy_priority.py  разрезы с приоритетом дорогих цветовых уровней
  registry.py        явная регистрация и выбор алгоритма
```

`src/rebar/optimization/__init__.py` — единственная рекомендуемая точка импорта для
потребителей. Внутреннюю структуру можно менять без переписывания CLI и отчёта.

Локальная визуализация вынесена из оптимизации в `src/rebar/reporting/`, а исполняемый
CLI остаётся тонким файлом `scripts/compare_optimizers.py`.

## Контракт алгоритма

Каждая реализация обязана иметь стабильное `name` и один метод:

```python
def solve(
    self,
    problem: LayoutProblem,
    request: AlgorithmRequest | None = None,
) -> LayoutSolution:
    ...
```

Алгоритм отвечает только за выбор разбиения. Он должен использовать общую детализацию и
не должен подменять правила оценки локальной формулой ради более выгодных метрик.

Целевой выходной контракт остаётся на уровне зоны:

```python
@dataclass(frozen=True)
class LayoutZone:
    id: str
    bbox: BBox
    level_index: int
    rebar: Rebar
    width_mm: float
    required_length_mm: float
    installed_length_mm: float
    bar_count: int
    mass_kg: float
```

При `width_mm = k × step` количество равно `k + 1`, а масса считается по одинаковой
`installed_length_mm` всех стержней зоны. Явные координаты каждого стержня в контракт не
добавляем без отдельного требования Revit-разработчика.

## Уровни решения и метрик

Текущий `LayoutProblem -> LayoutSolution` описывает **одно направление** армирования.
Его `metrics.detail_count` равен числу `LayoutZone`, а не числу стержней внутри них.

Для полного сценария нужен следующий агрегирующий слой в пакете оптимизации:

```text
PlateProblem
├── bottom-X: LayoutProblem
├── bottom-Y: LayoutProblem
├── top-X:    LayoutProblem
└── top-Y:    LayoutProblem

PlateSolution
├── direction_solutions: 4 × LayoutSolution
├── detail_count: sum(direction.detail_count)
├── total_mass_kg: sum(direction.total_mass_kg)
└── diagnostics/status
```

Это планируемые контракты, их ещё нет в коде. Они должны появиться в
`optimization/contracts/`, не в публичном ingest-контракте `models.py`.

Геометрические задачи четырёх направлений решаются независимо. Для построения общего
фронта Парето сначала получаем недоминируемые пары `(detail_count, total_mass_kg)` для
каждого направления, затем складываем четыре фронта динамическим программированием и
снова удаляем доминируемые комбинации. Так общий бюджет деталей распределяется между
направлениями без искусственного одинакового `max_details` для каждого.

`AlgorithmRequest.max_details` сейчас относится только к одному `LayoutSolution`.
Значение `4` в примере README — ручной smoke-test, а не найденная «Точка 3» и не итог
всей плиты.

Чтобы добавить следующий алгоритм, например `cpsat`:

1. создать отдельный файл `optimization/algorithms/cpsat.py`;
2. реализовать протокол без изменения `Mosaic` и существующих контрактов;
3. зарегистрировать класс в `built_in_optimizer_registry()`;
4. добавить общий поведенческий тест в `tests/optimization/test_algorithms.py`;
5. после этого имя автоматически можно передать в локальный отчёт через `--algorithms`.

## Текущие ограничения MVP

`bbox`, `bsp`, `greedy` и `greedy-priority` — сравнимые baseline, а не готовая
инженерная выдача.
Greedy сначала строит непересекающиеся поперечные полосы минимальной ширины, затем
объединяет соседние пары с наименьшим приростом целевой стоимости. Он быстрый и всегда
покрывает спрос в текущей модели, но не рассматривает произвольные прямоугольники и не
гарантирует глобальный оптимум.

`greedy-priority` использует те же допустимые гильотинные разрезы, что и BSP, но оценивает
их не только по немедленному снижению целевой функции. Дополнительный приоритет равен
оценке массы перерасхода, которую удаётся убрать, если сильный уровень больше не
назначается слабым КЭ. Вес задаётся `AlgorithmRequest.params["priority_weight"]`, по
умолчанию `1.0`. Это помогает изолировать дорогие уровни, но не снимает геометрические
ограничения `40d`, минимальной ширины и запрета пересечений.

Общие ограничения baseline:

- покрытие КЭ пока проверяется по попаданию центроида в прямоугольник;
- минимальная ширина оценивается как `min_width_cells × медианный поперечный размер КЭ`;
- используется безопасная рабочая семантика: одна деталь должна быть не слабее каждого
  накрытого ею требуемого КЭ;
- пересечения запрещены, но обязательный зазор на величину шага ещё не реализован;
- ширина зоны пока не всегда приводится к точному кратному шага;
- покрытие пока проверяется по центроиду КЭ, а не по полной геометрии;
- контуры проёмов и запрещённых областей пока отсутствуют во входном контракте;
- для DXF без `.shk` неизвестны диаметр и шаг, поэтому `DemandMap` построить можно, а
  `LayoutProblem` для детализации — нельзя.

Эти допущения сохраняются в `meta` результата и показываются в HTML. Следующий шаг —
заменять их подтверждёнными правилами внутри `services/`, не размножая разные трактовки
по алгоритмам.

## Следующий обязательный этап

До добавления CP-SAT/MILP и дальнейшего улучшения BSP нужно:

1. генерировать ширину строго как `k × step` и `bar_count = k + 1`;
2. учитывать `40d` с каждой стороны при геометрии и стоимости прямоугольника;
3. запретить пересечения и обеспечить зазор между соседними зонами на величину шага;
4. заменить центроидную аппроксимацию точной проверкой покрытия КЭ прямоугольником;
5. считать массу по параметрам зоны и строить Парето-кривую «масса ↔ число деталей»;
6. рисовать прямоугольники с выносками: длина, ширина, диаметр, шаг и количество;
7. покрыть правила синтетическими тестами X/Y и прогнать на реальном DXF.
8. добавить `PlateProblem`/`PlateSolution`, общий фронт четырёх направлений и агрегаты
   всей плиты.

После этого `bbox`, BSP, Greedy и CP-SAT/MILP можно честно сравнивать: все они получают
один `LayoutProblem`, выбирают только прямоугольники и проходят один общий валидатор.

Порядок работ и критерии локальной демонстрации собраны в
[`mvp-roadmap.md`](mvp-roadmap.md).
