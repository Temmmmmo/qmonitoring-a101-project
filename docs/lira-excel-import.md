# Числовой вход ЛИРА: три Excel, четыре направления

Реализовано 12 сентября 2026. Это первый этап
[плана после встречи](post-meeting-materials-2026-09-12.md): чтение исходной
потребности и адаптация к общему `DemandMap`. Это не готовая укладка в Revit.

## Что работает

- `rebar.lira.read_lira_excel(nodes, elements, reinforcement)` возвращает `LiraPlate`:
  узлы, КЭ, группы, исходные строки, все четыре As, вторые строки и SHA256 файлов.
- `application/inspect_lira_excel.py` формирует сводку и по запросу полные записи.
- `optimization/adapters/lira.py` принимает явно заданные шкалы, проверяет их
  пороги **и среднюю площадь стали** и строит четыре `DemandMap` с настоящими ID КЭ.
  Подбор не зависит от цветов и не создаёт фиктивную DXF-мозаику.
- CLI сохраняет новый JSON; существующий файл не перезаписывает.
- HTTP API принимает три XLSX, проверяет их общим сервисом, удаляет временные
  копии после ответа. Самостоятельной формы Excel в текущем web-интерфейсе пока нет.

Исходники открываются только для чтения. Excel/Revit, макросы и внешние связи
не запускаются. Для XLSX добавлены `openpyxl` и `defusedxml` в `requirements.txt`.
Используется [read-only режим с reset_dimensions и закрытием книги](https://openpyxl.readthedocs.io/en/stable/optimized.html);
защита XML соответствует [рекомендации библиотеки](https://openpyxl.readthedocs.io/en/stable/#security).

## Поддержанный профиль

ID: `lira-a101-plates-first-row-v1`. Он соответствует переданным А101 трём книгам,
не обещает чтение всех возможных форматов/версий выгрузки ЛИРА.

| Книга | Обязательные поля | Единицы |
| --- | --- | --- |
| Узлы | ID, X, Y, Z, заголовки единиц | м или мм; перевод в мм один раз |
| Элементы | ID, тип 42/44, одно сечение, тип жёсткости, угол, ссылки на узлы | ID сохраняются, не перенумеровываются |
| Арматура | ID группы и КЭ, AS1–AS4; две последовательные строки каждого КЭ | см²/м по инструкции профиля |
| Заголовок группы | h, бетон, Ax/Ay, шаг | h в см переводится в мм; шаг уже в мм |

AS1/AS2/AS3/AS4 — соответственно нижнее X / верхнее X / нижнее Y / верхнее Y
в **экспортных осях**. Перед превращением в `DemandMap` нужно явно подтвердить
совпадение этих осей с глобальными X/Y. Ненулевой локальный угол простой адаптер
отклоняет; `-` сохраняется как отсутствие значения, не как доказательство ориентации.

Первая строка каждого КЭ — полная потребность. Вторая хранится как
`second_row_as_cm2_m_unassigned`: ей не назначен смысл карты по прочности.
Парсер сверяет пары по ID и группе; новые заголовки нарушают глобальную чётность
строк, поэтому выбор `row % 2` недопустим. Если вторая строка больше первой,
этот профиль отказывается принимать непроверенный порядок/смысл строк.

### Порядок узлов: важное новое открытие

У всех 2 093 четырёхузловых КЭ этого набора исходный список идёт в порядке сеточных
узлов, а не обхода контура. Для КЭ 44 граница — **1–2–4–3**, для 42 — **1–2–3**.
`node_ids` и `vertices_mm` сохраняют исходный порядок;
`LiraElement.polygon_xy_mm` возвращает проверенный порядок границы.
Автоматическая сортировка по углам или замена на convex hull не применяется.

Это проверено не только совпадением множеств вершин: все 2 132 полученных полигона
совпали с DXF по границе (Hausdorff < 1e-6 мм) и симметрической разности площади
(< 1e-5 мм²). Прежняя сверка только наборов вершин не проверяла порядок обхода.

## Отказы и сохранение геометрии

Ошибкой всего комплекта являются: дубликаты ID, потерянные узлы/КЭ, неполные пары,
перепутанные группы/колонки, отрицательные или нечисловые As, формулы и ошибки Excel,
неизвестные/смешанные единицы, вырожденные/невыпуклые/наложенные КЭ, совпадающие
вершины под разными ID, разные отметки Z используемых узлов (> 0,001 мм).
Данные нельзя «починить» удалением проблемных строк или сплющиванием в XY.

Неиспользованные узлы сохраняются и перечисляются в отчёте; они не расширяют bbox
плиты. Расчётная толщина группы не подставляется вместо физической толщины host.
Пустоты в сетке не заполняются: это не доказательство границ реальных проёмов Revit.

Лимиты: файл 32 МиБ (в HTTP 30 МиБ), суммарно 128 МиБ распакованного XLSX,
512 ZIP-записей, 100 000 строк, 64 столбца, 10 000 КЭ. Требуется один видимый лист.
Макросы, внешние связи и повторяющиеся имена ZIP-записей отклоняются.

## Запуск

```bash
python3 -m pip install -r requirements.txt
python3 scripts/inspect_lira_excel.py \
  --nodes 'Для верификации изополей 2/Оцифровка изополей_фундамент/Узлы.xlsx' \
  --elements 'Для верификации изополей 2/Оцифровка изополей_фундамент/Элементы.xlsx' \
  --reinforcement 'Для верификации изополей 2/Оцифровка изополей_фундамент/Арматура в пластинах.xlsx' \
  --include-records --output artifacts/lira_numeric_import/source.json
```

Для адаптации к `DemandMap` CLI дополнительно принимает все четыре
`--shk-bottom-x`, `--shk-bottom-y`, `--shk-top-x`, `--shk-top-y` и
`--confirm-export-axes-global-xy`. Последний флаг — явное утверждение вызывающего,
не результат автоматической проверки и не одобрение конструктора.
Общий `.shk` допустим только при явной передаче его каждому подходящему направлению.
Дефицит до ближайшего рецепта не округляется вниз; составные рецепты сохраняются целиком.

HTTP: `POST /api/inspect-lira-excel`, multipart-поля `nodes`, `elements`, `reinforcement`;
необязательное `include_records=true`. Результат — JSON со статусом `collected`,
численными диапазонами четырёх направлений, группами и происхождением.
Ошибка входа — 422, пустой файл — 400, превышение размера загрузки — 413.
Имена клиентских файлов очищаются, для каждой роли используется отдельный каталог.

## Результат на предоставленном комплекте

2 209 узлов, 2 132 КЭ (39 треугольных и 2 093 четырёхузловых), шесть групп,
габарит 23 600 × 14 000 мм, Z = −8 970 мм. Лишних/потерянных ссылок нет.
Все четыре числовые карты проходят адаптацию на явно переданных совместимых шкалах
в тесте с заданным соответствием осей. КЭ 5281 и 5292 получают добавку при As2=8,82,
а не остаются фоновыми как в прежнем DXF. Окончательные инженерные параметры укладки
из этого теста не следуют.

На исходных файлах openpyxl предупреждает о нечитаемом колонтитуле. Это предупреждение
оформления сохраняется в журнале; данные всех строк проверяются, исходники не меняются.

Итог проверки этой итерации: **1 225 passed**, 106,81 с; из них **51 тест** нового
числового входа, адаптера, CLI и HTTP API. Три предупреждения относятся к колонтитулам
исходных Excel. Ruff, compileall и `git diff --check` прошли. Однокомпонентный
синтетический числовой вход дополнительно проверен через существующие оптимизатор
и hard-валидатор; составной вход старым GA не подменяется. Формат результата
CLI/HTTP при одинаковом `include_records` совпадает.

Следующий этап — осреднение/анкеровка по СТО и независимая проверка преобразованной
числовой карты. Однокомпонентный старый GA по-прежнему отклоняет составные шкалы;
полный составной поиск, раскрой партии и Revit apply/update ещё не объединены.
