# Четыре DXF → составная раскладка → общая ведомость и раскрой

Дата: 13 сентября 2026. Реализован один прикладной сценарий, общий для web и CLI.
Он обрабатывает **полный комплект четырёх направлений**, сохраняет все добавки из
шкал, сравнивает массу и позиции всей плиты, проверяет партию 11 700 мм. Это ещё
не законченный продукт с выпуском модели Revit: границы оставшейся работы ниже.

## Вход и запуск

Для первого знакомства: открыть **`/composite?demo=1`** — пример запустится сам,
или нажать «Посмотреть пример» на `/composite`. Никаких файлов или ручных фаз не нужно.
Создаются временные DXF/SHK синтетической плиты 6×4 м, 96 КЭ в каждом направлении;
геометрическая сетка общая, расположение уровней спроса различается. Используется
тот же application service, не заранее записанный удачный результат. Фазы 0/+150/+50,
класс A500 и предел прироста массы 5% явно помечены только как параметры демо.
Рабочая форма «Рассчитать свои DXF» не заполняется ими. Временные файлы удаляются
после запроса, включая ошибку; БД и материалы заказчика не используются.
HTTP: `POST /api/composite-demo` без тела, результат — обычный отчёт с дополнительным
`demo.source_kind=synthetic`. Маркер демо сохраняется и в скачанном черновике.

В web открыть `/composite` (ссылка есть на главной странице). Обычный запуск:

```bash
python3 -m uvicorn rebar.web.app:app --app-dir src --host 127.0.0.1 --port 8000
```

1. Загрузить четыре DXF: низ X/Y и верх X/Y. Для каждого указать соответствующий
   SHK или PNG с легендой; один и тот же файл допустимо явно выбрать в нескольких полях.
2. Задать начало фоновой сетки и смещения добавок, класс стали и источник выбора
   этих параметров. Для X поперечная координата — Y; для Y — X, в миллиметрах.
   Пустые поля не означают ноль. Класс стали не угадывается.
3. Указать лимиты зон, общеплитных позиций, бюджета поиска и прироста массы ради
   раскроя. Web начинает с 384 предложений на направление, допускает до 1 024.
   Бюджет MILP не включает генерацию и независимую геометрическую проверку; весь
   расчёт может длиться несколько минут. Web запускает его фоновым заданием и опрашивает
   статус отдельно, чтобы долгий POST не обрывался по таймауту прокси.
4. Для проверки контура приложить JSON Reference Probe и явно подтвердить совпадение
   XY. Без него можно исследовать варианты, но проверка границ остаётся незавершённой.
5. Результат: общеплитная кривая «масса ↔ позиции», четыре переключаемые схемы
   фактических осей, ведомость, схемы раскроя, причины отказов и JSON для скачивания.
   При отказе остаётся видна вся исходная мозаика, контуры host и проёмов;
   КЭ с доказанным противоречием продольным 40d у края выделены красным.

Ручное редактирование JSON для запуска web не требуется. Excel также не требуется:
он является отдельным числовым входом, а не условием DXF-сценария. Обоснование в
стенограмме встречи: **00:35:50–00:36:24** — передача трёх Excel для оцифровки;
**00:18:20–00:18:24** — допускается подходящий формат входа, даже PNG не обязателен.
Эти XLSX содержат числовые КЭ/узлы/As, не таблицу трудозатрат из `economic_info`.

Для программного клиента `POST /api/analyze-composite-plate` с полем формы
`async_job=true` возвращает `202` и `job_id`. Затем `GET
/api/analyze-composite-plate/jobs/{job_id}` возвращает `202` во время расчёта,
готовый JSON с `200` или HTTP-ошибку. Результат доступен час после завершения;
одновременно выполняется одно загруженное задание. Без `async_job` прежний
синхронный HTTP-контракт сохранён.

Поддержанный DXF-профиль: единая сетка КЭ четырёх направлений, фон @300, до двух
добавок @300 или условного @150; либо одна добавка @100 по описанной ниже схеме СТО.
Другие комбинации отклоняются. Цветовой спрос не подменяется числовым Excel:
два известных расхождения КЭ 5281/5292 остаются в [аудите источников](post-meeting-materials-2026-09-12.md).
Пакет фундамента и тестовая Revit-плита 300 мм не являются инженерно одинаковыми конструкциями.

CLI использует тот же `application/analyze_composite_plate.py`:

```bash
python3 scripts/analyze_composite_plate.py --help
```

Обязательны `--dxf-{bottom,top}-{x,y}`, `--shk-{bottom,top}-{x,y}` и
`--origin-{bottom,top}-{x,y}` (каждый флаг отдельно), `--first-300-offset`,
`--second-offset`, `--steel-class`, `--phase-source`, `--output`.
В отличие от web, CLI задаёт два смещения едиными для всех четырёх направлений.
`--reference` и `--confirm-host-xy` передаются вместе. Выход — **новый** JSON;
существующие файлы не перезаписываются. Код возврата 0 означает найденное полное
покрытие, а не разрешение Revit или прохождение всех гейтов; 1 — полного варианта
не найдено, 2 — ошибка входа/вызова. Обязательно смотреть статусы внутри отчёта.
CLI сохраняет исходный default `plate-11700`; совместный подбор включается явно
через `--cutting-profile plate-11700-batch`.

## Что изменилось в алгоритме

- `load_direction_mosaic` — общий DXF/SHK-ingest, без дублирования старого parser.
  Проверяется геометрия каждого КЭ один к одному, не только одинаковые габариты.
  Имена и SHA256 исходных DXF/SHK сохраняются; изменение файла во время чтения — ошибка.
- `composite_pool` строит составные прямоугольники с настоящими периодическими
  осями. Старый однокомпонентный GA не получает молча последнюю добавку шкалы.
- `finite_cover` учитывает активацию типоразмеров. Зона с двумя компонентами —
  не обязательно две позиции; одинаковые стержни разных зон объединяются.
- `combine_keyed_candidates` сохраняет минимальную массу для **каждого множества**
  типоразмеров до объединения четырёх направлений. Локально доминируемая точка
  с другим составом позиций может оказаться полезной всей плите. Лимит состояний
  вызывает явный отказ, а не скрытую эвристическую обрезку фронта.
- Каждый выданный вариант повторно проходит общий coverage; масса считается
  после анкеровки и назначения установленной длины. Полного варианта нет, если
  хотя бы одно направление не решено. Исходный спрос не понижается и не удаляется.
- Выбор центральной точки — прозрачная эвристика равновесия нормированных массы
  и позиций, не обученная «Точка 3» и не подтверждённый выбор конструктора.

Это конечный MILP-поиск и улучшение сквозного составного сценария, **не доказанное
улучшение генетического алгоритма**. Глобальный оптимум за пределами пула не заявляется.
Лимит `maximum_candidates` в текущем генераторе ограничивает уникальные предложения,
в том числе затем отвергнутые; фактическое число допустимых кандидатов — в telemetry.

## @100: сохранена схема СТО, а не равномерная сетка

Источник: `2026-07-31_СТО 5.5_рев3.pdf`, печатная страница **65**, раздел **2.7.3**,
таблица **2.7.9**. Проверены текст и рисунок. Рядом с фоном показан дополнительный
стержень, который должен укладываться вплотную, без зазора.

Явная исследовательская интерпретация для одинаковой высоты осей:
`δ = (d_фон + d_добавка)/2`. В периоде 300 мм добавка имеет оси
`100, 200, 300−δ` слева от ближайшего фонового стержня либо зеркальные
`δ, 100, 200` справа. Средний шаг — 100, фактические интервалы —
`100−δ, 100, 100+δ`, а не три одинаковых интервала. Это сохраняет количество и массу
при точном расчёте осей; **Z не назначен**, фактическое 3D-касание пока не подтверждено.

У первой добавки @150 сохранены оси `100, 200` относительно фона @300; один набор
Revit с равномерным шагом 150 не эквивалентен этой схеме. Фазы второй добавки и первой
@300 задаёт вызывающая сторона. Их инженерная применимость не подтверждается кодом.

Новая политика `a101-sto-279-ordered-recipe-contact/research-v1` отделена от старой.
Старый профиль таблицы 2.4.7 по-прежнему отвергает @100. Замечание по укладке
сохраняется в `installation_notes` нового отчёта; **формат компонента Revit v2
не расширялся**, исторический Core Trial остаётся совместимым.

## Безотходный раскрой: проверка и подбор — разные операции

`stock_cutting.py` независимо проверяет **фактическую партию**, а не наличие длины
в каталоге. Один диаметр и один класс стали образуют отдельную задачу. Каждая
заготовка — 11 700 мм, каждый установленный стержень назначается ровно один раз.
Запасные неустановленные детали, потерянные остатки и дополнительное количество
стержней не допускаются. Пропил принят нулевым; смешанные длины одного материала
разрешены **в модели**, производственное подтверждение отмечено `not_checked`.

Пример корректной схемы: `4 875 + 6 825 = 11 700` при совместимых количествах.
`8×1 460` и `7×1 670` сами по себе не безотходны. Кратность общей длины партии
необходима, но недостаточна: проверяется существование целочисленных количеств
схем и точное соответствие всей ведомости. Лимит времени/перебора — `not_checked`,
а не доказательство невозможности. Результат решателя проверяется независимо.

`plate-11700-batch` дополнительно вызывает `stock_length_balance.py`:

1. Для каждого уже выбранного компонента зоны перебираются длины каталога,
   **не меньшие** исходной установленной. Выбор один на компонент, число стержней
   и диаметры неизменны, регулярные ряды не превращаются в дополнительные детали.
2. MILP совместно выбирает длины компонентов и схемы раскроя. Ограничения:
   инвентарный баланс по классу/диаметру/длине, максимум позиций, прирост массы.
3. После решения повторяется независимая проверка партии; все четыре направления
   строятся заново общим детализатором. Проверяются покрытие, масса, количества,
   а при наличии host — границы/проёмы и поддержанные геометрические конфликты.
   Удлинение, нарушившее геометрию, отклоняется.

Default прироста — **5% к этому же исходному кандидату**, не к массе инженера.
Алгоритм не повышает предел при неудаче. Проверяются центральный и самый лёгкий
исходные варианты, если они различаются; уже безотходные точки также сохраняются.
Это ограниченный этап улучшения, не совместный глобальный поиск всех зон и раскроя.

При наличии успешных точек они образуют отдельный фронт `zero-waste-candidates`;
первоначальная кривая остаётся в `diagnostic_front_before_cutting`. Допустимые и
недопустимые по раскрою точки не смешиваются на одной кривой. При отсутствии
успешных точек показывается исходный coverage-фронт с явным провалом раскроя.

## Эксперименты на настоящих четырёх DXF

Все серии: 2 132 КЭ **в каждом** направлении, исходный спрос сохранён; фиксированные
40d с обоих концов, длины до 11 700 мм, минимум 2 КЭ, максимум 64 зоны на направление,
бюджет MILP 5 с на направление. Шкалы: нижние — `2025-08-15_ППТ8-1-Д2-К09_М1.shk`,
верхние — отдельные `К09_фп_2 фона_Вх.shk` и `К09_фп_2 фона_Ву.shk`.

Диагностические, **не согласованные** параметры серий: начала фона 0 мм,
смещение первой @300 +150 мм, второй добавки +50 мм, класс A500, касание @100 слева.
Высоты неизвестны. Серии ниже **без host**: ноль непокрытых КЭ доказывает только
покрытие в выбранной модели, не физическую готовность к размещению.

| Лимит предложений / направление | Минимум массы добавки, кг | Позиций | Зон | Стержней | Безотходный раскрой |
| --- | ---: | ---: | ---: | ---: | --- |
| 128 | 49 960,229 | 27 | 41 | 2 520 | Не выполнен |
| 384 | 44 485,326 | 26 | 70 | 2 713 | Не выполнен |
| 1 024 | 37 942,993 | 28 | 108 | 2 531 | Не выполнен |

Минимум при 1 024 ниже исходного на **24,05%**; стержней на 11 больше, позиций на
одну больше, зон на 67 больше. Нельзя выдать улучшение массы за одновременное
улучшение всех метрик. Бюджет генерации увеличен, поэтому это не равнобюджетный
A/B и не доказательство превосходства над инженером. Эталон 3 177,64 кг относится
к **другой плите** (плита нуля), сравнивать эти массы нельзя.

Подбор длин с лимитом +5% оказался несовместим в рассмотренных каталожных вариантах
центральной и минимальной точек как при 384, так и при 1 024 предложениях.
Вывод не распространяется на все остальные разбиения и возможные длины.

Отдельный диагностический запуск с пределом +100% нужен был для определения
минимальной стоимости этой гипотезы, **не для изменения рабочего ограничения**.
При исходных 44 485,326 кг решатель получил минимальные в данных вариантах
**48 790,729 кг / 25 позиций / 70 зон / 2 713 стержней**, рост **9,678%**,
нулевой остаток партии в модели реза. Для центральной точки 50 961,989 кг получилось
59 204,209 кг. Даже успешный раскрой не снимает вопросы границ, высот и фона.

С Reference Probe `051/qmonitoring-reference-20260910-095803-020000.json` строгая
проверка **не допускает полного результата**: продольным 40d у наружного края
противоречат 13 КЭ bottom X, 66 bottom Y, 67 top X и 60 top Y. Это счётчики
разных направлений, не число уникальных КЭ всей плиты. Ничего из спроса не вырезано.
В этом снимке проёмов нет; отдельные синтетические проверки проёмов выполнены.

Полные JSON хранятся локально в `artifacts/composite_plate_2026_09_13/`:
`real-full-128.json`, `real-full-384.json`, `real-full-384-batch.json`,
`real-full-1024-batch.json`, `diagnostic-overhead-bound-384.json`, `real-host-128.json`.
Они исключены из Git. Старые исследовательские отчёты не являются пакетами загрузки
в Revit; итоговый повтор на актуальном коде — `real-full-1024-batch-verified.json`.
Повтор подтвердил ту же минимальную массу, но дал 11 промежуточных точек вместо
10: ограниченный временем MILP не гарантирует идентичность всего конечного фронта.
Схема отказа host на актуальном renderer — `real-host-128-verified.json`.

## Что ещё действительно не готово

1. **Метод СТО 2.7.5/2.15 в рабочем поиске.** Формула анкеровки по As и проверке
   нескольких рядов, осреднение с опорами и переносом спроса ещё не реализованы.
   Сейчас 40d блокирует настоящий край. Нет оснований молча заменить его на 15d,
   исключить краевую полосу или считать погашенной потребность над проёмом.
2. **Полная пространственная укладка.** Нужно назначить профиль высот относительно
   граней, проверить фон + все добавки + X/Y, стыки и реальные зазоры. Пока нельзя
   считать выбранные плоские фазы производственно допустимыми.
3. **Связь с рабочей Revit-моделью и выпуск.** Нет проверенного полного размещения,
   повторного обновления без дублей, общеплитного readback и нативной маркировки/
   спецификаций по шаблону А101. Старые Windows trials подтверждают только свой
   ограниченный сценарий с откатом, а не готовность партии реальной плиты.
4. **Сквозная приёмка на совпадающем исходнике.** Масса добавки, позиции,
   общий расход с существующим армированием и формальные гейты должны проверяться
   на одной версии рабочей плиты. Текущий набор исходников не даёт права объявить
   числовую победу над другой инженерской спецификацией.

Порядок дальнейшей разработки: метод СТО и реальный край → совместная геометрия
всех направлений → полный apply/update/readback и ведомости → сквозная приёмка.
Загибы, муфты и сварка в объём не добавляются. Имитировать готовность одной зоной
или оставлять краевые КЭ вне задачи не допускается.

## Проверки кода и границы проверки

Тесты охватывают HTTP → настоящий DXF/SHK parser → четыре направления → фронт и
ведомость; CLI и запрет перезаписи; несовместимые шкалы/геометрию/направления,
пустые фазы и NaN; полное сохранение спроса при отказе границ/проёмов; @100 и
несовместимость равномерной подмены; независимые малые переборы позиций и длин;
ложные векторы MILP и баланс раскроя; неизменность количества при удлинении;
совместимость исторического Revit v2.

Результат регрессии: **1 325 passed**, 109,98 с, три предупреждения openpyxl о
неразобранных колонтитулах реальных XLSX (не потеря строк армирования). После
финальной доработки отображения исходного спроса/контуров/проблемных КЭ повторно
прошли **42** application/HTTP-теста. Ruff, compileall, Node `--check` и
`git diff --check` проходят. Реальный повтор host подтвердил 2 132 видимых исходных
полигона в каждом направлении и ровно 13/66/67/60 выделенных КЭ.
Также выполнен настоящий multipart POST на запущенный локальный uvicorn с восемью
файлами реального комплекта: 2 132 КЭ × четыре направления, 8 вариантов при лимите
128, минимум 49 960,229 кг, все статусы раскроя `fail`, размещение запрещено.
Для CLI-проверки через curl JSON нужно передавать `--form-string`, не `-F`:
пунктуация внутри значения не должна интерпретироваться как синтаксис формы curl.

Wheel собирается с новыми Python-модулями и web-ресурсами. Runtime-зависимости
