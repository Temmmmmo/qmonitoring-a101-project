# План интеграции с Revit и сообщение Revit-специалисту

Дата: 2026-08-27
Статус: рабочий план первой итерации; Python-экспорт `draft` реализован 29 августа

## Короткое решение

Интеграцию предлагается строить без участия нейросети в контуре размещения арматуры:

```text
4 DXF + mapping/.shk + настройки
                ↓
        Python API / готовый JSON
                ↓
   выбранный и проверенный PlateSolutionRevitV1
                ↓
     PreviewPlateSolution в Revit
                ↓
      ApplyPlateSolution в Revit
                ↓
  AreaReinforcement + обратная проверка результата
```

Основные решения первой итерации:

- одна `LayoutZone` представляется одной `AreaReinforcement`;
- хостом является выбранная пользователем плита;
- четыре направления `bottom/top × X/Y` передаются одним выбранным решением;
- плагин поддерживает два источника одного и того же контракта:
  - отправить четыре DXF в Python API и получить JSON;
  - открыть ранее сохранённый JSON;
- оба режима после загрузки вызывают один детерминированный сценарий
  `ApplyPlateSolution()`;
- основная привязка координат выполняется по выбранному в Revit импортированному или
  связанному DXF (`ImportInstance`);
- RevitCortex можно использовать для быстрого технического spike, но он не заменяет
  контракт, проверки и специализированную команду применения решения;
- Revit-специалист отвечает за модель, настройки и инженерную приёмку, но от него не
  требуется разработка на C#.

Revit 2024 использует .NET Framework 4.8. RevitCortex заявляет отдельную конфигурацию
`Debug R24`, поэтому технически подходит как кандидат для эксперимента. До установки в
рабочей среде всё равно нужны локальная проверка сборки, разрешение на add-in и
согласование режима `send_code_to_revit`.

Числовой `ElementId` плиты полезно получить для первичного поиска, но не следует делать
его единственной долгоживущей ссылкой. В контексте запуска плагин сохраняет
`Element.UniqueId` и всё равно просит пользователя подтвердить выбранный хост.

## Границы первой версии

Поддерживаем:

- горизонтальную плоскую конструктивную плиту;
- прямоугольные зоны;
- прямые параллельные стержни;
- локальные направления X/Y исходного DXF;
- перенос и поворот всего DXF относительно модели Revit;
- четыре слоя/направления: нижняя X, нижняя Y, верхняя X, верхняя Y;
- предварительный просмотр, применение, откат и повторную проверку.

Пока не поддерживаем:

- стержни, расположенные по диагонали относительно локальных осей исходного DXF;
- криволинейную раскладку;
- наклонные и сложные многогранные хосты;
- автоматическое исправление зон, попавших в проёмы или за границу плиты;
- автоматический выпуск рабочей документации без проверки конструктора;
- использование LLM для вычисления координат или принятия инженерных решений.

Поворот импортированного DXF в модели не считается «диагональной арматурой»: локальные
X/Y вместе поворачиваются матрицей импорта. Ограничение относится к направлениям,
которые уже диагональны или криволинейны внутри самого DXF.

## Что именно передаёт Python

Текущий web-ответ `schema_version: 4` предназначен для интерфейса и содержит лишние
представления, SVG и варианты фронта. Его не следует напрямую делать контрактом Revit.
Нужен отдельный компактный экспорт только выбранного кандидата.

Первая версия этого отдельного экспорта уже реализована. Web добавляет к выбранному
plate-кандидату `revit_export`, показывает кнопку скачивания и не включает в файл SVG и
остальные точки фронта. Схема остаётся `draft`: до согласования с Revit-специалистом и
подключения каталога А101 поле `checks.export_eligible` равно `false`, а причины
перечислены в `blocking_check_ids`.

Черновой состав `PlateSolutionRevitV1`:

```json
{
  "schema_version": "plate-solution-revit/v1",
  "units": "mm",
  "case_id": "plate-zero",
  "coordinate_reference": {
    "source_id": "bottom-x.dxf",
    "source_sha256": "...",
    "system": "source-dxf-wcs"
  },
  "candidate": {
    "id": "plate-candidate-001",
    "algorithm": "mixed-pareto",
    "ruleset_id": "research-v1",
    "status": "feasible"
  },
  "checks": {
    "direction_count": 4,
    "under_reinforced_cell_count": 0,
    "export_eligible": true,
    "diagnostics": []
  },
  "directions": [
    {
      "layer": "bottom",
      "axis": "x",
      "zones": [
        {
          "id": "bottom-x-zone-001",
          "bbox_mm": [1000.0, 2000.0, 7000.0, 3200.0],
          "demand_bbox_mm": [1480.0, 2000.0, 6520.0, 3200.0],
          "diameter_mm": 12,
          "step_mm": 200,
          "bar_count": 7,
          "first_bar_coordinate_mm": 2000.0,
          "required_length_mm": 5040.0,
          "anchored_length_mm": 6000.0,
          "installed_length_mm": 6000.0,
          "width_mm": 1200.0
        }
      ]
    }
  ]
}
```

Значение полей:

- `bbox_mm` — установленный envelope осей после анкеровки и раскроя; именно он является
  исходной геометрией для построения области и осей в Revit;
- `demand_bbox_mm` — исходная область потребности только для аудита и визуального
  сравнения, а не геометрия размещаемых стержней;
- `first_bar_coordinate_mm`, `step_mm` и `bar_count` должны однозначно восстанавливать
  все поперечные оси;
- `installed_length_mm` является фактической принятой длиной;
- координаты и длины остаются в миллиметрах и в системе исходного DXF.

Все четыре DXF должны быть предварительно проверены на совместимость координат. В
экспорте фиксируется один опорный DXF и его fingerprint; для связанного файла плагин
сверяет его с выбранным `ImportInstance`. Для импортированного файла, где исходный путь
может быть недоступен, обязательна геометрическая проверка масштаба и контрольной точки.

`export_eligible` — отдельный строгий гейт экспорта, а не простое переименование
текущего `PlateSolution.valid`: до его реализации нужно явно определить, какие
диагностики и неподтверждённые правила запрещают передачу в Revit.

Точная граница `AreaReinforcement`, позволяющая воспроизвести эти оси, должна быть
подтверждена техническим spike: нельзя считать корректным результат только потому, что
объект успешно создался через API.

Контекст конкретной модели Revit не входит в доменный результат Python. Его собирает
плагин:

```text
PlacementContext
├── host_floor_unique_id
├── cad_import_unique_id или контрольные точки
├── зафиксированная матрица преобразования
├── соответствие diameter_mm → RebarBarType
├── защитный слой и дополнительные смещения
├── режим preview/apply/replace
└── идентификатор запуска
```

## Совмещение координат

### Основной режим: выбранный DXF в Revit

1. Пользователь выбирает `ImportInstance` того же DXF, по которому рассчитано решение.
2. Плагин получает `GetTotalTransform()` выбранного экземпляра.
3. Плагин строит отдельное преобразование единиц из миллиметров DXF во внутренние
   единицы Revit.
4. Для точек применяется преобразование с переносом, для направлений — без переноса.
5. Масштаб проверяется по известному отрезку или контрольным точкам, а не принимается
   молча.
6. XY переводятся в координаты модели Revit. Z определяется по геометрии выбранной
   плиты, защитному слою и слою арматуры.

Концептуально:

```text
P_revit = T_total.OfPoint(S_mm_to_local(P_dxf))
V_revit = Normalize(T_total.OfVector(S_mm_to_local(V_dxf)))
```

Перед preview и перед apply плагин должен проверить:

- выбран именно ожидаемый DXF;
- преобразование не изменилось между preview и apply;
- масштаб конечный и подтверждён контрольным размером;
- преобразование конформно;
- отражение отсутствует — отражённые импорты в первой версии отклоняются;
- преобразованные углы зоны попадают на выбранный хост в пределах допуска.

Простого совмещения по одному «нулю» недостаточно: одна точка определяет перенос, но не
проверяет поворот, масштаб и отражение.

### Резервный режим: контрольные точки

Если соответствующий DXF не загружен в Revit, пользователь задаёт пары точек
`DXF ↔ Revit`:

- две пары позволяют вычислить перенос и поворот при заранее известном масштабе;
- три неколлинеарные пары позволяют проверить масштаб, ориентацию и остаточную ошибку;
- применение запрещается, если ошибка совмещения превышает согласованный допуск.

Для MVP предпочтителен режим с выбранным `ImportInstance`; контрольные точки — второй
этап, а не параллельная обязательная реализация.

## Представление `LayoutZone` в Revit

Предварительное отображение одной зоны:

- объект: `AreaReinforcement`;
- хост: выбранная плита;
- граница: прямоугольник, полученный из установленного `bbox_mm`;
- major direction: преобразованный вектор локальной оси X или Y;
- активен только один требуемый слой `top/bottom × major`;
- тип стержня выбирается по `diameter_mm`;
- шаг задаётся из `step_mm`;
- остальные слои области отключены;
- `zone.id`, `case_id`, `candidate.id` и `run_id` сохраняются как служебная маркировка,
  чтобы повторный запуск работал только со своими объектами.

В spike нужно проверить, воспроизводит ли `AreaReinforcement` требуемые крайние оси,
число стержней и длину. Если API не позволяет получить нужную геометрию без скрытой
коррекции Revit, второй вариант реализации — создавать управляемые наборы обычных
стержней. Это решение принимается только по результату измерения в тестовой модели.

## Один сценарий применения

```text
LoadFromApi(...) ─┐
                  ├─→ ValidatePlateSolution(...)
LoadFromJson(...) ┘              ↓
                         BuildPlacementContext(...)
                                  ↓
                         PreviewPlateSolution(...)
                                  ↓
                          ApplyPlateSolution(...)
                                  ↓
                         ReadBackAndValidate(...)
```

`ApplyPlateSolution()` должен:

1. повторно валидировать версию схемы и статус выбранного кандидата;
2. проверять комплект четырёх направлений и отсутствие недоармирования;
3. проверять хост, типы стержней, защитный слой и преобразование координат;
4. открыть одну `TransactionGroup` на весь запуск;
5. создать области для всех зон;
6. прочитать фактические параметры созданных объектов через Revit API;
7. сравнить их с JSON;
8. выполнить rollback всей группы при любой критической ошибке;
9. при успехе сохранить отчёт применения и идентификаторы созданных объектов.

По умолчанию повторный запуск не удаляет и не изменяет чужие элементы. Режим `replace`
может заменять только элементы с тем же `case_id/candidate.id`, ранее созданные нашим
плагином.

## План работ

### Этап 0. Зафиксировать входы и критерий приёмки

Статус входных материалов:

- [x] версия — Revit 2024.3;
- [x] способ привязки — импортированный DXF;
- [ ] копия тестовой RVT-модели;
- [ ] исходный DXF и этот же DXF, импортированный в модели;
- [ ] выбранная тестовая плита: ID, а при запуске также выбор и `UniqueId`;
- [ ] используемые `RebarBarType` для нужных диаметров;
- [ ] защитный слой;
- [ ] одна вручную созданная эталонная `AreaReinforcement`;
- [ ] скриншот и ожидаемые параметры одной простой зоны;
- [ ] корпоративная трактовка верх/низ — нужна до полной плиты, но не до spike;
- [ ] политика проёмов, краёв и пересечений — нужна до полной плиты, но не до spike.

Результат этапа: одна согласованная зона и чек-лист, по которому специалист отвечает
«да, расположение и параметры правильные».

### Этап 1. Технический spike одной зоны

- подготовить минимальный JSON с одной зоной;
- выбрать плиту и `ImportInstance`;
- получить и запротоколировать преобразование;
- создать одну `AreaReinforcement`;
- включить только один слой;
- вернуть из Revit фактические параметры;
- проверить rollback и отсутствие изменений посторонних элементов.

Для скорости spike можно выполнить через `RevitCortex/send_code_to_revit`. Его цель —
проверить API и семантику `AreaReinforcement`, а не построить финальный продукт.
Однозонный spike использует отдельную экспериментальную команду и не ослабляет будущую
проверку полного четырёхнаправленного `PlateSolutionRevitV1`.

Критерий выхода: специалист подтверждает расположение, слой, направление, диаметр и
шаг; автоматическая проверка подтверждает количество и геометрию стержней.

### Этап 2. Надёжная привязка координат

- проверить неповёрнутый DXF;
- проверить тот же DXF с переносом и поворотом;
- проверить единицы по контрольному отрезку;
- добавить отказ при неверном масштабе и отражении;
- определить Z по поверхности хоста и защитному слою;
- зафиксировать матрицу между preview и apply.

Критерий выхода: одна и та же зона совпадает с ожидаемым местом для неповёрнутого и
повёрнутого импорта.

### Этап 3. Выделенный JSON-контракт и два режима загрузки

Python:

- определить dataclass/сериализатор `PlateSolutionRevitV1`;
- экспортировать только выбранный допустимый кандидат;
- добавить JSON Schema и тесты round-trip;
- не включать в экспорт UI/SVG и весь Парето-фронт;
- добавить отдельный API-ответ или endpoint для Revit.

Revit:

- загрузка готового JSON с диска;
- вызов Python API с четырьмя DXF;
- одинаковая десериализация и `ValidatePlateSolution()` для обоих режимов.

Критерий выхода: один JSON даёт одинаковый preview независимо от способа получения.

### Этап 4. Полная плита

- применить 3–5 зон одного направления;
- затем применить четыре направления;
- добавить мэппинг диаметр → тип стержня;
- сохранять связь `zone.id → Revit UniqueId`;
- реализовать безопасный повторный запуск и `replace` только своих объектов;
- сформировать отчёт применения.

Критерий выхода: полный тестовый комплект создаётся одной операцией либо целиком
откатывается.

### Этап 5. Инженерная приёмка и решение о реализации

- Revit-специалист визуально проверяет модель и вид;
- код сравнивает расчётные и фактические параметры;
- конструктор/технолог подтверждает политику пересечений, проёмов и выхода за плиту;
- команда решает, оставить ли RevitCortex как зависимость или вынести
  `ApplyPlateSolution` в минимальный C# add-in;
- фиксируются установка, ограничения и сценарий восстановления.

Критерий выхода: подписанный чек-лист тестовой модели. Результат всё ещё называется
черновиком для проверки конструктора, а не автоматически выпущенным решением.

## Чек-лист автоматической и ручной проверки

Для каждой зоны Revit должен вернуть:

- `zone_id`;
- `AreaReinforcement.UniqueId`;
- `host.UniqueId`;
- слой и направление;
- тип стержня и фактический диаметр;
- фактический шаг;
- фактическое количество стержней;
- координаты первой и последней оси;
- фактические длины;
- предупреждения Revit.

Проверки:

| Проверка | Начальный критерий для spike |
|---|---:|
| Хост | точное совпадение `UniqueId` |
| Слой | точное совпадение |
| Диаметр | точное совпадение |
| Количество стержней | точное совпадение |
| Шаг и длина | отклонение не более 1 мм |
| Координаты крайних осей | отклонение не более 2 мм |
| Направление | отклонение не более 0,1° |
| Посторонние изменённые элементы | 0 |
| Ошибка одной зоны | rollback всего запуска |

Допуски в таблице предварительные; перед production их должен подтвердить специалист.

Обязательные тестовые сценарии:

1. Одна зона, DXF без поворота.
2. Одна зона, DXF перенесён и повёрнут.
3. Несколько зон одного направления.
4. Четыре направления одной плиты.
5. Ошибочный масштаб — применение запрещено.
6. Отражённый импорт — применение запрещено в v1.
7. Неизвестный диаметр/тип — применение запрещено до транзакции.
8. Ошибка в середине создания — все созданные элементы откатываются.
9. Повторный запуск — чужие элементы не изменяются.

## Готовый ответ Revit-специалисту

> Спасибо, этого уже достаточно, чтобы зафиксировать направление. Целевая версия у нас
> теперь Revit 2024.3, DXF для первого теста используем импортированный. Модель можно
> выложить на любой привычный закрытый ресурс с доступом по ссылке — в публичный GitHub
> её загружать не нужно.
>
> По плите пришли ID, но при самом запуске мы ещё попросим выбрать её в модели и
> зафиксируем `UniqueId`, чтобы не полагаться только на числовой ID. Типы арматуры,
> защитный слой, ручная `AreaReinforcement` и скриншот можно подготовить вместе с
> моделью.
>
> Ответы конструкторов про верх/низ, проёмы, края и наложения ждать для первого теста не
> нужно. Возьмём одну однозначную зону вдали от проёмов, края плиты и других зон. Сначала
> хотим проверить только базовую вещь: можно ли через API в Revit 2024.3 получить
> `AreaReinforcement` с правильным положением, направлением, диаметром, шагом,
> количеством и длиной. Уже после этого будем расширять правила.
>
> По срокам предлагаю такой ориентир: если удобно, минимальный комплект материалов —
> модель, DXF, выбранная плита, тип/cover и одна эталонная зона — хотелось бы получить
> до 2 сентября. После получения нам нужно до двух рабочих дней на подготовку
> однозонного теста и совместную проверку. Ещё 2–3 рабочих дня заложим на перенос,
> поворот и масштаб координат, если первый тест пройдёт.
>
> Это не жёсткий дедлайн для тебя: если из-за загрузки удобна другая дата, просто назови
> её, и мы сдвинем график. Срок полной интеграции назовём после однозонного теста, потому
> что главный неизвестный сейчас — насколько `AreaReinforcement` подходит для нашей
> точной геометрии.
