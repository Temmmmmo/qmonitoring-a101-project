# Составной поиск и реальное противоречие у края — 10 сентября 2026

Продолжение по согласованию с пользователем:
[частичный внутренний поиск и отрицательная проверка качества](composite-interior-research-2026-09-10.md).
Новый `interior-exceptions` не устраняет описанное ниже противоречие полной задачи:
край остаётся нерешённым, 12,06 т внутри не являются подтверждённым улучшением.
Строгий профиль и запрет размещения сохранены.

## Вывод

Исследовательский поиск теперь работает с **обеими дополнительными компонентами**
настоящего Top X из `2 фона`. Все выданные точки проверены на покрытие по фактическим
периодическим осям, без сложения слабых зон. Это **не готовое размещение**:
host-проверка отвергает все четыре найденных варианта.

Более сильная, независимая от поиска проверка установила противоречие текущей
физической модели на **67 КЭ / 5 786 020,174 мм² спроса**. Не утверждаем, что плита
вообще не может быть заармирована: несовместимы именно наши прямые стержни с 40d за
границы `demand_bbox`, выбранная модель покрытия и размещение внутри данного host.
Изменить инженерное правило автоматически нельзя.

## Что реализовано

- `contracts/composite_search.py`: отдельные задача, точка и результат поиска.
  Публичный `models.py` не менялся; прежний `LayoutProblem` по-прежнему отклоняет
  несколько добавок, старые GA и production-export не получили скрытого fallback.
- `algorithms/composite_pool.py`: конечный пул прямоугольников из многоуровневых
  разрезов по геометрии КЭ, каждый совместимый **полный** рецепт сохраняется.
  Это отдельный research CLI, не зарегистрированный оптимизатор прежнего web.
- `services/composite_windows.py`: явное расширение окна до необходимых крайних
  обслуживающих осей; минимальная ширина окна и кратность НОК номинальных шагов.
  Это не автоматическая подрезка по host и не подтверждение ширины каждого набора.
- `services/finite_cover.py`: ограниченный SciPy/HiGHS MILP, масса при лимитах числа
  зон. Стоимости поступают из общей детализации после 40d/раскроя. В матрице один КЭ
  должен целиком покрываться одним достаточным кандидатом; фрагментные объединения
  валидатор умеет, но этот поиск их дополнительно не использует.
- Каждая выбранная раскладка повторно проходит независимый
  `evaluate_composite_coverage`. Ответ решателя сам по себе не является `pass`.
  Дробные, неполные и превышающие лимит предложения не принимаются.
- Default выбирает на конечном mass/zone-count фронте минимум суммы квадратов
  нормированных расстояний до идеальных значений, с равными весами. При равенстве
  предпочитается меньшая масса. Это прозрачная исследовательская эвристика,
  не подтверждённое предпочтение конструктора и не доказанная «Точка 3».
- `contracts/host.py`, `services/composite_host.py`: фактические оси всех добавок,
  плоские торцы, радиус, боковой/верхний/нижний cover, прямоугольные сквозные проёмы,
  наложения зон одного направления и столкновения известных по высоте стержней.
  Ничего не обрезается. Проверка расстояния у торцов для коллизий и резерв проёма
  консервативны; спорный контакт выдаёт ошибку, а не разрешение.
- `application/composite_host_review.py`: наружный контур определяется геометрией,
  а не номером петли; верх/низ должны иметь совпадающие прямоугольные контуры.
  Наклонные/криволинейные/несовпадающие грани не подменяются bbox. В Reference Probe
  нет полного Solid: боковые грани, несквозные полости и актуальная модель остаются
  `not_checked`, даже если проверка переданного envelope успешна.
- `application/optimize_composite_layout.py` и CLI: ingest → общая конфигурация фаз →
  поиск → независимый review → опциональная host-проверка. `placement_eligible=false`
  во всех режимах. `report-only` исследует фронт и показывает его нарушения;
  `require-planar-containment` отбрасывает нарушающие host кандидаты и известные
  конфликты выбранных наборов. При доказанном краевом противоречии останавливается
  **до** построения пула/вызова solver со статусом `engineering_decision_required`.

Высоты компонентов пока отсутствуют в JSON research-конфиге и не выбираются
автоматически. Поэтому Z/3D в реальном эксперименте `not_checked`. Сервис принимает
явные глубины в типизированном контракте, тесты проверяют верх/низ и оба направления.
Межнаправленные столкновения, существующий фон, согласование фаз, нормативные
сочетания, раздвижка и Revit readback остаются отдельной работой.

## Почему одним тюнингом край не исправить

Для обязательной добавки Ø18 удлинение с каждой стороны ≥40×18=720 мм.
При боковом cover 25 мм и плите X=0…23 599,999 мм допустимая продольная граница
спроса прямой зоны должна быть внутри **745…22 854,999 мм**. Если zone начинается
раньше, её фактический стержень после 40d нарушает cover. Анкеровку нельзя засчитать
в покрытие по текущему research-контракту.

Для зон с обязательной Ø25 необходимый отступ ещё больше: 1000+25 мм.
Раскрой может лишь увеличить этот отступ, поэтому проверка — необходимое условие,
не приближённая стоимость кандидата. Всего **67 КЭ** пересекают запрещённые
продольные полосы. **7 КЭ слева и 6 справа** непосредственно касаются X=0/23600.
Переразбиение и изменение фазы не устраняют этого противоречия. При этом найденное
условие ничего не говорит о возможности другого инженерного узла у края.

Нужны решение конструктора о краевой анкеровке/трактовке границ спроса и один
показанный участок. Не уменьшать 40d, не скрывать КЭ, не подрезать автоматически
и не называть это доказанной невозможностью армирования плиты.
[Готовое короткое сообщение от первого лица](revit-edge-question-2026-09-10.md).

## Воспроизведение

Требуется optional-зависимость `pip install -e '.[solver]'`; без SciPy — явная ошибка.
Конфиг — `composite-layout-review-input/v1` с **пустым** `zones`, всеми фазами шкалы
и источником их выбора. Остальные поля описаны в журнале
[составного покрытия](composite-coverage-research-2026-09-09.md).

```bash
artifacts/ga_solver_env/bin/python scripts/optimize_composite_layout.py \
  --dxf 'Дополнительные материалы/Изополя(мозаики) армирования/2 фона/Верхнее армирование вдоль ОСИ Х.dxf' \
  --shk 'Дополнительные материалы/Изополя(мозаики) армирования/2 фона/К09_фп_2 фона_Вх.shk' \
  --config artifacts/composite_search_2026_09_10/research-phases.json \
  --output /tmp/new-composite-search.json \
  --maximum-candidates 1024 --maximum-zones 64 --partition-depth 8 --solver-time-limit 30 \
  --reference revit_info/051/qmonitoring-reference-20260910-095803-020000.json \
  --coordinate-policy explicit-source-xy-equals-reference-xy/research-v1 \
  --host-policy require-planar-containment
```

Без последней строки — исследовательский фронт с host-диагностикой. XY-политика —
явное условие офлайн-проверки, не live-привязка. Для 051 согласованность координат
отдельно доказана [source-binding checker](revit-source-binding-2026-09-10.md).
Исходники хешируются до/после; output должен быть новым `.json`, overwrite запрещён.
Exit 0 означает найденный **research**-фронт, 1 — отсутствие решения/инженерное
противоречие, 2 — ошибку входа. Даже exit 0 не разрешает размещение.

Артефакты (игнорируются Git): `artifacts/composite_search_2026_09_10/` —
`research-phases.json`, `front-128.json`, `front-1024.json`, `front-1024-host.json`,
`strict-host-blocked.json`. Первые отчёты сохранены без перезаписи; строгий
`strict-host-certificate.json` фиксирует новый явный статус инженерного решения.
