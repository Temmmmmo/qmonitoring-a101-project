# Revit в web-приложении

`/revit` — рабочая страница скачивания инструментов, установки и инспекции JSON-снимков.
Она доступна с главной страницы и из `/composite`. Содержимое страницы не зависит
от локальных `artifacts/`, моделей, исходных DXF или частных отчётов.

## Что уже работает

| Инструмент | Вкладка | Действие в Revit |
| --- | --- | --- |
| Working Host Probe 0.1.0 | `QMonitoringHostTools` | Только чтение выбранной плиты, защитных слоёв, Solid и выбранного CAD |
| Working Rebar Probe 0.1.0 | `QMonitoringReadOnly` | Только чтение Rebar/RebarInSystem выбранной native-плиты и их фактических положений |
| Plan Preview 0.1.1 | `QMonitoringPreview` | После подтверждения создаёт один новый чертёжный вид; не создаёт конструктивную арматуру |

Каждый ZIP содержит одну кнопку, только её явные runtime-зависимости, README и
manifest. Новые вкладки не требуют отключать старую `QMonitoring.extension`.
Для установки в pyRevit добавляется **родительская папка**, внутри которой лежит
соответствующая `.extension`. При обновлении удаляют из настроек только прежний
путь той же extension, а не другие инструменты. Сам pyRevit в ZIP не включён.

Ни один установочный пакет не содержит RVT/DXF/PDF, частных JSON, демоплиты или
готовой раскладки. Разрешение на размещение и инженерное подтверждение всегда false.
Библиотеки общих проверок внутри Plan Preview также используются другими trial-командами,
но сами кнопки структурного создания в этот whitelist не включены.

## HTTP-контракт

- `GET /revit` — страница с инструкцией и карточками.
- `GET /api/revit/tools` — `qmonitoring-revit-tools/v1`: версии, возможности,
  совместимые входные схемы, вкладки, инструкции, имена файлов, размер, SHA256 и URL.
- `GET /api/revit/tools/{tool_id}/{version}/download` — `application/zip`, всегда
  `Content-Disposition: attachment`. Только точные ID/версии из whitelist;
  неизвестная версия или попытка подставить путь даёт 404.
- `POST /api/revit/inspect-snapshots` — multipart с необязательными файловыми полями
  `host` и `rebar`; хотя бы одно обязательно. Возвращает
  `qmonitoring-revit-snapshot-inspection/v1`, не пакет расчёта или размещения.

ID инструментов: `working-host-probe`, `working-rebar-probe`, `plan-preview`.
`runtime_version` — версия исходного pyRevit-модуля; `version` дополнительно содержит
16 hex-символов хеша содержимого. Изменение зависимости, инструкции или возможностей
создаёт новую версию ссылки. ZIP воспроизводим: фиксированные дата/права/порядок
элементов, ZIP STORE без зависимости от версии zlib. Типичные размеры порядка
70/64/174 КБ; точное число берётся из текущего каталога.

`X-Content-SHA256` и `ETag` содержат SHA256 точных ZIP-байтов. Версионные успешные
скачивания кешируются как `private, max-age=31536000, immutable`; каталог, страница,
JS/CSS и ошибки — `no-store`. Авторизация остаётся у Caddy согласно
[`deployment.md`](deployment.md); endpoint не открывает отдельный внешний порт.

Перед выдачей каталога и архива приложение проверяет наличие и SHA256 всех нужных
ресурсов. Повреждённая или неполная поставка даёт 503 с объяснением, не подменяется
поиском старого пакета в `artifacts/`.

## Инспекция переданных снимков

Поддержаны только `revit-working-host-cad-probe/v1` и `revit-working-rebar-probe/v1`
в соответствующих полях. Лимит — **32 MiB суммарно на оба JSON**, плюс не более
64 KiB на multipart-обёртку. Полный wire body ограничивается **до** multipart-разбора
и временного spooling файлов, в том числе без Content-Length. Разбор принимает
только два уникальных файловых поля, не текстовые формы или дополнительные файлы.
Стандартный multipart-парсер закрывает временные файлы и при успехе, и при ошибке.
API не создаёт постоянных файлов, ссылок скачивания или записей в БД; исходные данные
живут только в памяти/временном хранилище на время запроса. Браузер не записывает их
в localStorage/sessionStorage. Авторизацию на развёрнутом сервере обеспечивает Caddy.

JSON проверяется целиком: UTF-8, уникальные ключи, отсутствие NaN/Infinity и
переполненных `1e999`, глубина до 64, до 2 млн значений/ключей, строка до 200 тыс.
символов, целые в 64-битном диапазоне. Поля идентификаторов и подписей ограничены
отдельно. Небезопасный/неподдержанный формат — 422, превышение байтового лимита — 413.
SHA256 считается по **точным загруженным байтам**; это идентификатор файла,
не подпись Revit и не доказательство подлинности.

Для плиты показываются ID/UID, отметка, bbox, защитные слои и число записей Solid.
Топология этих граней, отверстия, совпадение DXF и реальный host здесь **не проверяются**.
Для арматуры сводка пересчитывается по уникальным ElementId/UniqueId и position index:
прочитанные/исключённые/непрочитанные положения, положения с поддержанными записями
Line/Arc, Area/Path-родители (не вторые копии стержней), закрытые worksets,
неподдержанные native-элементы, замечания чтения. Несогласованная сводка или ложный
флаг полноты отклоняется. `complete_as_reported` означает согласованность записей,
**не независимую проверку кривых в RVT**; `partial` не превращается в нулевую
или полную инвентаризацию. Показаны первые 50 замечаний и полное количество;
числа и проверки не обрезаются этим лимитом отображения.

Сопоставление двух снимков различает несовпадение host UID/ID или project UID,
совпадение доступных UID и недостаточную идентичность документа. Старый Working Host
Probe не пишет project-information UID: совпадения UID плиты и строкового пути
недостаточно для подтверждения документа. Сам путь не возвращается; возвращается
его хеш для сопоставления и название модели. Разные пути могут означать разные
локальные копии. Даже одинаковые UID могли сохраниться после копирования RVT,
поэтому **актуальность или идентичность текущего открытого RVT никогда не заявляются**.

Во всех ответах `placement_eligible=false`, `engineering_approval=false`,
`live_model_checked=false`, `source_inputs_retained=false`,
`connected_to_calculation=false`. Инспектор не определяет инженерную роль стержней
по диаметру/имени, не считает геометрический факт прохождением анкеровки/покрытия,
не проверяет арматуру других hosts и связей.

Multipart-ограничения и закрытие UploadFile основаны на штатном
[Request API Starlette](https://starlette.dev/requests/). Его `max_part_size` сам по себе
не ограничивает файлы; поэтому отдельный лимит тела запроса здесь обязателен.

## Wheel, Docker и read-only runtime

`application/revit_installation.py` содержит stdlib-only whitelist и сборщик.
`setup.py` расширяет `build_py`: после копирования Python-модулей генерирует
`rebar/web/revit_bundles/catalog.json` и три ZIP прямо в каталоге сборки wheel.
`MANIFEST.in` перечисляет точные исходные файлы pyRevit для пересборки из sdist.
Алгоритмы, SciPy и Revit DLL во время этого build hook не импортируются.

Docker копирует публичный код интеграции и три кнопки на этапе установки пакета.
Закрытые материалы и `artifacts/` по-прежнему исключены Docker context. В установленном
приложении ресурсы читаются через `importlib.resources`: корень репозитория и запись
на диск не нужны, поэтому схема совместима с read-only root filesystem в production.

В dev-режиме разрешена сборка ZIP в памяти **только для распознанного checkout**:
текущий модуль должен лежать в его `src/`, рядом должны быть `.git`, `AGENTS.md` и
`pyproject.toml`. Произвольный путь из HTTP/переменной окружения не принимается.
Если установленных ресурсов нет и это не checkout, приложение не ищет материалы
где-нибудь на машине и отвечает 503.

Проверка в CI: обычный `pip wheel` и Docker build запускают тот же hook. Дополнительно
тестируются HTTP, content-addressing, точные ZIP-файлы и зависимости импортов,
отсутствие структурных кнопок/частных данных, повреждённые ресурсы, traversal,
stdlib-only сборка и обслуживание ресурсов без checkout/записи.

## Границы текущего сценария

Сегодня через страницу можно скачать инструменты, снять данные и запустить
графический просмотр уже подготовленного совместимого физического пакета.

Загрузка новых снимков host/rebar и их read-only инспекция реализованы. Их
автоматическое подключение к расчёту пока **не реализовано**: совпадение UID не
подменяет привязку исходных DXF и проверку физического решения. После чтения нужно
сохранить исходные JSON у себя. База данных, серверный Revit RPC и фоновое подключение
к рабочим моделям не добавлены.

Plan Preview принимает `physical-bar-plan-trial/v1` и
`physical-bar-relocation-draft/v1`. Общий `composite-plate-analysis/v1` и JSON,
скачанный обычной кнопкой составного расчёта, не объявляются совместимым пакетом.
В этой поставке нет генерации/экспорта новых форм и нет команды автоматического
создания полного структурного решения. Новые схемы алгоритма нужно подключать
отдельным проверенным адаптером, не ослабляя старый валидатор.

Working Rebar Probe 0.1.0 ещё требует первого реального запуска Revit.
Plan Preview 0.1.1 уже проверен реальным отчётом 14 сентября, 17:36: создан и
зафиксирован новый вид 13809056, обратное чтение совпало для 902/902 графических линий
при допуске 0,01 мм; конструктивных Rebar создано 0. Исходный частный JSON в поставку
не включён. Этот факт подтверждает графическое отображение, не инженерную выдачу.
Наличие download endpoint и локальных тестов также не означает инженерной приёмки;
`collected` обозначает чтение, а не расчётную готовность.
