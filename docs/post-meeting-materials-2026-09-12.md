## Числовой вход ЛИРА

Файлы в `Оцифровка изополей_фундамент/`:

| Файл | Содержимое и проверка |
| --- | --- |
| `Узлы.xlsx` | 2 209 уникальных узлов; XYZ в метрах; после перевода в мм габарит 23 600 × 14 000, Z = −8 970 |
| `Элементы.xlsx` | 2 132 КЭ: 39 треугольных типа 42 и 2 093 четырёхузловых типа 44 |
| `Арматура в пластинах.xlsx` | 4 264 числовых строки, по две на каждый из 2 132 КЭ, плюс заголовки |

Ссылки на узлы замкнуты; неиспользованных узлов нет. Множества ID элементов
в геометрии и армировании совпадают. Формул в этих трёх книгах нет: это числовые
результаты, не экономическая модель. Книга армирования не записывает размеры листа
в обычном заголовке XLSX; импортёр не должен считать `max_row=None` пустым листом.

В инструкции (последняя страница) прямо предписано брать **первую строку каждого КЭ**:
это полное армирование. Вторую строку нельзя складывать с первой, усреднять с ней
или автоматически назначать потребностью «по прочности» без отдельного разбора.
Например, в Top X первая и вторая строки различаются у 799 КЭ. Экспортёр должен
сохранять номер исходной строки, ID элемента и группу, а не полагаться на глобальную
нечётность строк: между группами вставлены заголовки.

Значения AS1–AS4 означают соответственно bottom X, top X, bottom Y, top Y,
единицы — см²/м. Это сверено с [документацией ЛИРА](https://help.liraland.com/pdf/2019/kniga_otcheta/Kniga_otcheta_sample_panel.pdf).
Нужно проверять локальные оси оболочек и преобразование к осям проекта; символ `-`
в колонке угла сам по себе не сертификат ориентации всех будущих входов.

Диапазоны полного армирования в проверенной выгрузке:

| Направление | Минимум, см²/м | Максимум, см²/м |
| --- | ---: | ---: |
| bottom X | 7,20 | 89,10 |
| top X | 7,20 | 57,78 |
| bottom Y | 7,20 | 50,59 |
| top Y | 7,20 | 37,79 |

В заголовках шесть групп оболочек: h = 80, 220, 203, 168, 133 и 98 **см**, бетон B30,
продольная арматура Ax/Ay A500, исходный шаг 300 мм. Это 800–2 200 мм расчётной
толщины, а не 80–220 мм. Нужно сохранить её по КЭ и сопоставить с рабочей геометрией;
не переносить автоматически эквивалентную расчётную толщину в физический Revit-host.
Тестовая плита 300 мм остаётся стендом API, не инженерным эквивалентом этого фундамента.

### Сверка с ранее использованным Top X DXF

Геометрия всех 2 132 КЭ сопоставлена один к одному с
`Дополнительные материалы/Верхнее армирование вдоль ОСИ Х.dxf`.
Максимальное расхождение XY вершин около `1,1e-11 мм`, Z совпадает.
Предварительная индексация с округлением давала 117 ложных несовпадений на границах
округления; проверка фактических вершин их устранила. Одного округлённого хеша недостаточно.

Визуальные границы шкалы DXF `8,5 / 25 / 42 / 58` округлены. По ним возникают
15 несовпадений числового спроса с цветом. Соответствующий четырёхполосный `.shk`
имеет пороги около `8,483 / 25,45 / 41,81 / 58,18`; после его применения остаются
**два содержательных расхождения**, КЭ **5281 и 5292**: Excel AS2 = **8,82 см²/м**,
а цвет DXF — фон Ø18@300 с порогом около **8,483 см²/м**. Причина расхождения
не установлена; совпадение геометрии не доказывает совпадения версий потребности.

Для нового числового сценария сохранять исходные 8,82, а не понижать их до фона.
Источник требований выбирать явно; не выдавать результат старого DXF за проверку
полного числового Excel. Все четыре направления численно присутствуют уже в одном
комплекте из трёх XLSX — четыре цветовых изображения для этого входа не обязательны.

## Осреднение по СТО

Источник: `2026-07-31_СТО 5.5_рев3.pdf`, раздел 2.15, страницы 125–136.

- Таблица связывает ширину осреднения с толщиной конструкции; для промежуточных
  толщин прямо указана интерполяция ширины. Например, для 300 мм указано 750 мм;
  для толстых плит от 800 мм — 1,5t. Табличные ширины местами округлены, поэтому
  коэффициент и напечатанная ширина не всегда дают буквально одинаковое число.
- Для тонкой плиты возле опоры на странице 126 описаны 3t в каждую сторону;
  возле среднего пилона — 6t + ширина пилона, возле крайнего — 3t + ширина пилона.
  Нельзя считать табличное b универсальной полной шириной любого окна.
- Осредняется площадь армирования с весами по ширинам пересечённых участков:
  `As_avg = Σ(As_i · b_i) / Σb_i`. Это не среднее цветов и не понижение любого
  геометрически одиночного КЭ на один уровень.
- При исключении полосы пилона из размещения потребность этой полосы сохраняется,
  но доступная ширина уменьшается. Пример страницы 132:
  `(23,3×0,2 + 16,6×0,3 + 6,73×0,3) / 0,6 = 19,4317`,
  вместо деления на 0,8 и результата 14,57375. Исключить геометрию без переноса
  требуемой площади было бы ошибкой.
- Пример толстых плит на странице 134 даёт 13,14 и 28,68 см²/м для двух полос
  шириной по 1,5 м при t = 1 м. Эти примеры подходят для независимых тестов.
- На странице 130 разрешено игнорировать конкретный изолированный КЭ с As = 3,02
  рядом с фоном. Универсального числового критерия удаления всех одиночных пиков
  этот пример не задаёт. Старое безусловное понижение не становится подтверждённым.

Для автоматического применения нужны границы полос перераспределения, геометрия
опор, локальные толщины и протокол «исходное требование → преобразованное».
Пока эти операции не реализованы, приложение сохраняет исходную потребность.
Отключённое осреднение теперь означает «не применено», а не «СТО не получено».

## Анкеровка и проблема края

Источник: СТО 2.7.5, страницы 68–74; примеры 2.15, страницы 128–136.

СТО допускает расчёт длины по соотношению требуемой и установленной площади:
`l_an = α1 · l0_an · As_cal / As_ef`. В рассмотренном случае растянутой арматуры
α1 = 1. Упрощение `l0_an = 40d` относится к базовой длине в приведённых условиях,
а не обязательно к окончательному одинаковому выпуску с обоих концов любой зоны.
Проверяются конструктивные минимумы; документ приводит 15d и 200 мм и поясняет,
почему в этих примерах 0,3l0_an не определяет минимум. Нельзя переносить это
пояснение на произвольные материалы с другой базовой длиной.

Примеры рассматривают несколько рядов с собственной потребностью, расстоянием
от исходного ряда и длиной анкеровки; берётся определяющий габарит.
Формула для одного последнего КЭ без проверки остальных рядов не воспроизводит метод.
Допускается использовать полную расчётную площадь вместо отдельной карты по прочности,
если расход не превышает проектных значений (страница 133).

Это новая обоснованная гипотеза улучшения массы и допустимости возле края.
Она **не доказывает**, что все ранее найденные крайние КЭ теперь размещаются:
нужно пересчитать их на числовом входе с реальными гранями, опорами и материалами.
Не заменять 40d повсеместно на 15d и не маскировать недостаток длины обрезкой.
Загибы, муфты, приямки со специальными гнутыми узлами и сварку пользователь не
заказывал; эти технологии не добавляются в продукт из-за примеров внутри СТО.

## Раскрой из 11 700 мм

Источник: переданное пользователем письмо А101 после встречи. Заказчик требует,
чтобы после резки прутка 11 700 мм не оставалось отходов.

Текущий каталог `plate-11700` — **не доказательство безотходности**.
Например, в нём есть 1 460 и 1 670 мм: восемь и семь одинаковых отрезков оставляют
20 и 10 мм соответственно. Есть и дополняющие друг друга длины:
4 875 + 6 825 = 11 700. Значит, нужно различать округление длины отдельного стержня
и ведомость фактического раскроя партии с учётом диаметров, класса и количества.

Не округлять длину вниз ради раскроя. Не объявлять неиспользованный остаток «запасом»
и не добавлять лишние неустановленные стержни ради зелёного показателя отходов.
Требование можно реализовать схемами раскроя, но разрешение именно смешанных схем
и учёт технологического реза не конкретизированы письмом. В MVP необходимо явно
описывать выбранную модель реза и проверять её по каждой заготовке.
Разрешения на сварку в ответе нет.

## Revit и расходы

Рабочий `VTNK-02_RD_KR_K09_KJ.rvt` по пояснению содержит фундамент, плиту над −2,
плиту нуля и плиту над первым этажом. Второй RVT содержит комплект над 3–14 этажами.
Шаблон передан как `Шаблон РК Onefile_V2.rvt`, а не `.rte`; это не отсутствие шаблона.

В строковых метаданных всех трёх RVT обнаружены `Format: 2022` и build
`20230915_1530(x64)`. Это предварительное чтение, не запуск Autodesk API.
Регламент указывает Revit 2024.1, специалист работает в 2024.3.4.
Перед тестом нужно подтвердить версии через BasicFileInfo и открыть отдельные копии
в целевом Revit. Обновлённая копия не должна перезаписать исходник:
[Autodesk предупреждает об отсутствии обратной совместимости](https://help.autodesk.com/cloudhelp/2024/ENU/Revit-GetStarted/files/GUID-E7EB9EDD-4167-4F64-9688-D7E7B7934806.htm).

Проверенные требования `00. Стандарт информационного моделирования ГК А101_2.6.docx`:

- 3.1.5: армирование отделено от опалубки/изоляции рабочими наборами. На тестовой
  несовместной модели нельзя заявлять эту проверку пройденной или автоматически
  включать совместную работу.
- 3.2: масса, маркировка и остальные данные берутся из параметров элементов;
  текст, не связанный с элементом, не заменяет параметрическую ведомость.
- 3.4.2: спецификации и ведомости делаются средствами Revit, армирование —
  физическими 3D-элементами, включая фон и конструктивную арматуру.
  Наш модуль автоматизирует добавку; существующий фон нельзя пропускать в проверках
  пересечений и общих расходов, но это не поручение автоматизировать всё КЖ здания.
- 3.4.2 требует моделирования отверстий порядка 150 мм и больше на стадии РД.
  Порог моделирования не разрешает провести стержни через уже существующее отверстие.
- Параметр конструкции `ФОП_ТИП_Армирование` выражается в кг/м³; на стадии РД
  требуется актуальный коэффициент по соответствующей группе конструкций.

`Расходы армирования по плитам.docx`, таблица 2.6.4, — ограничения общего расхода
на объём бетона: например, 120 кг/м³ для указанного фундамента 17-этажного дома,
130 для перекрытий паркинга, 120 для плиты нуля, 130 для типовых плит 200 мм.
Это **не трудозатраты** и **не масса только добавки**. Для проверки нужны полный
состав армирования и корректный объём конструкции. Не сравнивать нашу добавку с
общим лимитом, выдавая это за полный контроль расхода.

## Что уже меняется в коде этой итерации

До поступления пакета начата поправка по стенограмме встречи: отдельная номенклатура
прямых стержней, ось `position_count` в GA, MILP и общеплитном выборе, ведомость
позиций в web/черновом JSON. При объединении направлений используется множество
типоразмеров, не сумма счётчиков; разные множества одинакового размера не отсекаются
до сборки плиты. Неизвестный класс стали явно остаётся неизвестным.

Приложение сохраняет исходный спрос; старое понижение одиночных КЭ доступно только
как `legacy-research`, его изменения отражаются отдельным блокирующим экспорт гейтом.
СТО не подключён автоматически на основании одного наличия файла.

Аудит исходников и сравнительные JSON находятся локально в
`artifacts/meeting_materials_2026_09_12/`. Они не являются поставкой или разрешением
на размещение. Исходные документы, Excel и RVT не редактировались.
